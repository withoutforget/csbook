# Статическая и динамическая типизация

Система типов — одно из ключевых архитектурных решений при проектировании языка программирования. Она определяет, когда и как проверяется корректность операций с данными: на этапе компиляции или во время исполнения, явно или с выведением типов, жёстко или с допустимыми преобразованиями. Выбор системы типов влияет на продуктивность разработчика, производительность программы, качество диагностики ошибок и выразительность кода.

Дискуссия "статическая vs динамическая типизация" нередко превращается в религиозный спор. Реальность богаче: современные языки размывают эту границу. Python получает аннотации типов с проверкой через mypy, TypeScript добавляет статику к JavaScript, а Dart и Kotlin позволяют динамически-типизированный режим. В этой статье мы разберём концепции строго, разберём компромиссы обоснованно и рассмотрим, как системы типов реализованы внутри компиляторов и интерпретаторов.

Понимание систем типов необходимо не только авторам языков, но и разработчикам, выбирающим инструменты, архитекторам API и всем, кто хочет осознанно использовать возможности и ограничения своего языка.

## 1. Фундаментальные понятия

### 1.1 Тип как контракт

Тип — это множество значений и набор операций, допустимых над ними. Тип `int` — это множество целых чисел с операциями +, -, *, /, сравнения. Тип `string` — последовательность символов с конкатенацией, поиском, срезами.

Система типов — формальная система, определяющая правила присвоения типов выражениям и проверки их совместимости. Цель — обнаружить программы, которые "бессмысленны" (divide a string by a number), до или во время их выполнения.

### 1.2 Статическая типизация

При **статической типизации** тип каждого выражения известен в момент компиляции. Компилятор проверяет совместимость типов до запуска программы.

```java
// Java — статическая типизация
int x = 42;
String s = "hello";
int result = x + s; // ОШИБКА КОМПИЛЯЦИИ: несовместимые типы
```

```haskell
-- Haskell — статическая типизация с выведением типов
add :: Int -> Int -> Int
add x y = x + y

-- Компилятор вычисляет тип без явных аннотаций
triple x = x * 3  -- :: Num a => a -> a
```

### 1.3 Динамическая типизация

При **динамической типизации** тип связан со значением, а не с переменной. Проверка происходит во время выполнения.

```python
# Python — динамическая типизация
x = 42
x = "hello"  # переменная может менять тип
x = [1, 2, 3]  # и снова

def add(a, b):
    return a + b  # тип аргументов неизвестен до вызова

add(1, 2)      # 3
add("a", "b")  # "ab"
add(1, "b")    # TypeError: unsupported operand type(s) for +: 'int' and 'str'
               # Ошибка только при выполнении!
```

### 1.4 Сильная и слабая типизация

Эти термины ортогональны статической/динамической типизации:

- **Сильная типизация**: неявные преобразования типов ограничены или запрещены. Python — динамический, но сильно типизированный: `1 + "2"` — ошибка.
- **Слабая типизация**: широкие неявные преобразования. JavaScript: `1 + "2"` → `"12"`, `"5" - 3` → `2`.

```javascript
// JavaScript — динамический, слабо типизированный
console.log(1 + "2");    // "12" (число приведено к строке)
console.log("5" - 3);    // 2   (строка приведена к числу)
console.log([] + {});    // "[object Object]"
console.log({} + []);    // 0 (в выражении) или "[object Object]" (в консоли)
console.log(false == 0); // true
console.log(null == undefined); // true
console.log(null === undefined); // false
```

Матрица:

| | Статическая | Динамическая |
|--|------------|-------------|
| **Сильная** | Java, C#, Haskell, Rust | Python, Ruby |
| **Слабая** | C (приведения указателей) | JavaScript, PHP (ранние версии) |

## 2. Реализация внутри компилятора

### 2.1 Таблица символов и среда типов

Компилятор статически типизированного языка поддерживает **таблицу символов** — отображение имён на типы. При каждом объявлении переменной в таблицу добавляется запись; при каждом использовании — тип проверяется.

```
Пример для: int x = 5; float y = x + 2.0f;

Таблица символов:
  x → int
  y → float

Проверка x + 2.0f:
  type(x) = int → продвигаем до float (integer promotion)
  type(2.0f) = float
  type(int + float) = float → OK
  type(float y = float) → OK
```

Для лексических областей видимости таблица организована как стек сред: при входе в блок создаётся новая среда, при выходе — удаляется.

### 2.2 Вывод типов (Type Inference)

Многие статически типизированные языки не требуют явных аннотаций благодаря выводу типов.

**Алгоритм Хиндли-Милнера** (HM) — классический алгоритм вывода типов для языков с параметрическим полиморфизмом (ML, Haskell, OCaml). Он линеен по времени и полон — всегда выводит наиболее общий тип.

```ocaml
(* OCaml — вывод типов HM *)
let identity x = x
(* Тип: 'a -> 'a (полиморфный, работает для любого типа) *)

let add x y = x + y
(* Тип: int -> int -> int (оператор + конкретизирует тип) *)

let double_list lst = List.map (fun x -> x * 2) lst
(* Тип: int list -> int list *)
```

Алгоритм основан на **унификации**: из выражений порождаются уравнения для типовых переменных, затем решаются через подстановку.

```
Выражение: fun x -> x + 1

Порождаем переменные: x : 'a, результат : 'b
Уравнения:
  (+) : int -> int -> int
  x : 'a унифицируется с int → 'a = int
  1 : int
  результат : int

Тип: int -> int
```

В C++11 появился `auto`, в Java 10 — `var` — более ограниченный локальный вывод типов:

```cpp
auto x = 42;                    // int
auto v = std::vector<int>{};    // std::vector<int>
auto it = v.begin();            // std::vector<int>::iterator

// Но НЕ вывод для параметров функций (в отличие от Haskell)
// auto add(auto x, auto y) { return x + y; } — только в C++20 (concepts)
```

### 2.3 Теговые значения в динамических языках

В динамически типизированных языках каждое значение несёт с собой тег типа. В CPython каждый объект — структура PyObject:

```c
// Упрощённая PyObject в CPython
typedef struct _object {
    Py_ssize_t ob_refcnt;    // счётчик ссылок для GC
    PyTypeObject *ob_type;   // указатель на тип!
} PyObject;

// Целое число
typedef struct {
    PyObject ob_base;
    Py_ssize_t ob_ival;  // само значение
} PyLongObject;

// При x + y Python делает:
// 1. Читает ob_type у x и y
// 2. Смотрит tp_as_number->nb_add в таблице типа
// 3. Вызывает соответствующую функцию
// Это несколько косвенных вызовов на каждую операцию
```

Отсюда фундаментальная разница в производительности: `1 + 1` в C — одна инструкция ADD; в Python — десятки операций с кучей косвенностей.

### 2.4 NaN-tagging и pointer tagging

Современные интерпретаторы (V8, LuaJIT, JavaScriptCore) используют **NaN-tagging** или **pointer tagging** для уменьшения overhead тегирования.

NaN-tagging: IEEE 754 double имеет 2^52 - 1 NaN-представлений (quiet NaN). Интерпретаторы используют эти "тихие NaN" для хранения указателей и целых чисел прямо в double-значении:

```
63     62-52    51-0
[sign] [11111111111] [payload]  — NaN pattern

Если не NaN:       → обычное число double
NaN + payload=ptr → указатель на объект в куче
NaN + payload=int → 32-битное целое
NaN + payload=xxx → null, true, false, undefined
```

Это позволяет хранить все значения в одном 64-битном слове без отдельной структуры тега — значительное ускорение для числовых вычислений.

## 3. Дженерики и полиморфизм

### 3.1 Параметрический полиморфизм

Обобщённые типы (generics) позволяют писать код, работающий с любым типом:

```java
// Java Generics — параметрический полиморфизм
public class Stack<T> {
    private List<T> items = new ArrayList<>();
    
    public void push(T item) { items.add(item); }
    
    public T pop() {
        return items.remove(items.size() - 1);
    }
}

Stack<Integer> intStack = new Stack<>();
Stack<String> strStack = new Stack<>();
// Тип проверяется на уровне компилятора
```

### 3.2 Type Erasure vs Monomorphization

Два фундаментально разных подхода к реализации дженериков:

**Type Erasure** (Java, Kotlin): тип параметра стирается при компиляции; во время выполнения всё превращается в Object. Один байт-код для всех инстанцирований.

```java
// После компиляции (псевдокод):
public class Stack {
    private List items = new ArrayList();
    public void push(Object item) { items.add(item); }
    public Object pop() { return items.remove(items.size() - 1); }
}
// Кастование происходит при извлечении
```

Минус: нельзя написать `new T()`, `T.class`, примитивы нужно боксить.

**Monomorphization** (C++, Rust): для каждого набора параметров генерируется отдельный код. `Stack<int>` и `Stack<String>` — разные машинные коды.

```rust
// Rust — monomorphization
fn largest<T: PartialOrd>(list: &[T]) -> &T {
    let mut largest = &list[0];
    for item in list {
        if item > largest { largest = item; }
    }
    largest
}

// Компилятор генерирует:
// largest_i32(list: &[i32]) -> &i32 { ... }
// largest_f64(list: &[f64]) -> &f64 { ... }
```

Сравнение:

| | Type Erasure | Monomorphization |
|--|------------|-----------------|
| Размер бинарника | Меньше | Больше (code bloat) |
| Производительность | Хуже (boxing, casts) | Лучше (инлайн, оптимизации) |
| Рефлексия типа | Ограничена | Ограничена (Rust) |
| Примитивные типы | Boxing required | Нативные |

### 3.3 Structural typing vs Nominal typing

**Номинальная типизация**: тип определяется именем. Два класса с одинаковыми полями — разные типы (Java, C#, Rust).

**Структурная типизация**: тип определяется структурой (duck typing). Если у объекта есть нужные методы — он подходит:

```go
// Go — структурная типизация через интерфейсы
type Writer interface {
    Write([]byte) (int, error)
}

// Любой тип, имеющий метод Write с нужной сигнатурой,
// автоматически реализует Writer — без явного объявления
type MyWriter struct{ buf []byte }
func (w *MyWriter) Write(p []byte) (int, error) {
    w.buf = append(w.buf, p...)
    return len(p), nil
}

// MyWriter реализует Writer неявно
var w Writer = &MyWriter{} // OK!
```

TypeScript использует структурную типизацию:

```typescript
interface Point { x: number; y: number; }

function distance(p: Point): number {
    return Math.sqrt(p.x**2 + p.y**2);
}

// Объект без явной реализации Point — но подходит структурно
distance({ x: 3, y: 4, name: "origin" }); // OK — лишние поля допустимы
```

## 4. Система типов Rust: владение как тип

Rust выводит типизацию на новый уровень, кодируя в системе типов владение памятью и время жизни:

```rust
// Время жизни (lifetime) — часть типа в Rust
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}

// 'a означает: результат живёт не дольше наименьшего из x и y
// Компилятор проверяет это статически — use-after-free невозможен

// Аффинные типы: значение можно использовать не более одного раза
fn consume(v: Vec<i32>) {
    println!("{:?}", v);
} // v удаляется здесь

let data = vec![1, 2, 3];
consume(data);
// consume(data); // ОШИБКА: value moved, нельзя использовать снова
```

Система типов Rust — это в некотором роде статический анализ управления памятью, встроенный в сам язык. Ошибки use-after-free, double-free, data race — это ошибки типов.

## 5. Gradual typing: лучшее из двух миров?

Gradual typing позволяет смешивать статически и динамически типизированный код в одной программе. Тип `Any` (или `dynamic`) совместим с любым другим типом.

### 5.1 Python с mypy

```python
# Python 3.5+ с аннотациями типов
from typing import List, Optional, Dict

def greet(name: str) -> str:
    return f"Hello, {name}!"

def find_user(users: List[Dict], user_id: int) -> Optional[Dict]:
    for user in users:
        if user['id'] == user_id:
            return user
    return None

# Проверка mypy:
# mypy script.py
# Success: no issues found

# Без аннотаций — Any, mypy не проверяет
def untyped_function(x):
    return x + "string"  # mypy не обнаружит ошибку здесь
```

mypy поддерживает постепенное внедрение: можно аннотировать по одному файлу, не ломая остальной код.

### 5.2 TypeScript

TypeScript — надстройка над JavaScript с опциональной статической типизацией:

```typescript
// TypeScript
interface User {
    id: number;
    name: string;
    email?: string; // опциональное поле
}

function formatUser(user: User): string {
    return `${user.name} (${user.id})`;
}

// Ошибка компиляции:
formatUser({ id: "not-a-number", name: "Alice" }); // Type 'string' is not assignable to type 'number'

// Тип any — выход из системы типов
function dangerous(x: any): any {
    return x.whatever.you.want; // нет проверки
}

// unknown — безопаснее any: нужно сужение типа перед использованием
function safe(x: unknown): string {
    if (typeof x === 'string') return x.toUpperCase();
    throw new Error('Expected string');
}
```

### 5.3 Dart: sound null safety

Dart 2.12 ввёл **sound null safety** — гарантию на уровне системы типов, что null не может появиться там, где тип не допускает его:

```dart
String name = "Alice";    // не может быть null
String? nullableName;     // может быть null

// Компилятор требует проверки перед использованием
print(nullableName.length); // ОШИБКА: nullable value
print(nullableName?.length); // OK: null-aware оператор
print(nullableName!.length); // OK: явное утверждение (кинет исключение если null)
```

## 6. Производительность: цена гибкости

### 6.1 Число операций на простое сложение

```python
# Python: a + b для int (упрощённо)
# 1. Проверить ob_type у a → int
# 2. Найти nb_add в таблице типа
# 3. Проверить ob_type у b → int
# 4. Вызвать int.__add__(a, b)
# 5. Выделить новый PyLongObject
# 6. Установить ob_refcnt = 1
# 7. Вернуть указатель
# ~50-100 инструкций процессора

# C: a + b для int
# ADD eax, ebx
# 1 инструкция
```

Это фундаментальное ограничение: динамическая диспетчеризация неизбежно дороже статической.

### 6.2 JIT как частичное решение

JIT-компилятор (V8, PyPy, JVM HotSpot) компилирует горячий код во время выполнения, специализируя его под реально наблюдаемые типы:

```
PyPy: если в цикле всегда a=int, b=int
→ компилирует: ADD eax, ebx
→ guard: если тип изменится — деоптимизация
```

PyPy ускоряет Python в 5-10 раз на числовых задачах. V8 делает JavaScript сопоставимым с Java. Но JIT добавляет стартовую задержку (warm-up) и непредсказуемость.

### 6.3 Измеримая разница

Примерные данные для идентичного алгоритма (обход массива + сумма):

| Язык | Время | Причина |
|------|-------|---------|
| C | 1x | Нативный код |
| Rust | ~1x | Нативный код |
| Java (JIT) | 1-3x | JIT-компиляция |
| Go | 2-4x | AOT, garbage collector |
| JavaScript (V8) | 3-10x | JIT, dynamism |
| Python (CPython) | 50-100x | Интерпретатор, PyObject |
| Python (PyPy) | 5-15x | JIT для Python |

Числа ориентировочные — зависят от задачи, паттернов доступа к памяти, GC.

## 7. Системы типов и надёжность ПО

### 7.1 Исследования о корреляции типизации и ошибок

Академические исследования дают неоднозначные результаты. Gao et al. (2017) проанализировали 400 JavaScript проектов: 15% ошибок могли быть предотвращены TypeScript. Ray et al. (2014) проанализировали GitHub: статически типизированные языки в среднем имеют меньше дефектов, но разброс велик.

Проблема методологии: проекты на статически типизированных языках часто имеют другую культуру разработки (тесты, code review), что затрудняет изоляцию влияния системы типов.

### 7.2 Type-driven development

Популярный паттерн в Haskell, Elm, Idris: сначала написать типы, потом реализацию. Если программа компилируется — она с высокой вероятностью корректна.

```haskell
-- Тип как документация и спецификация
data PaymentStatus = Pending | Completed | Failed String

processPayment :: Amount -> CreditCard -> IO PaymentStatus
-- Тип говорит: берём сумму и карту, возвращаем IO-действие
-- Результат — одно из трёх состояний

-- Компилятор заставляет обработать все случаи:
handleStatus :: PaymentStatus -> String
handleStatus Pending = "Ожидает обработки"
handleStatus Completed = "Успешно"
handleStatus (Failed reason) = "Ошибка: " ++ reason
-- Пропустить случай = ошибка компиляции
```

### 7.3 Dependent types (зависимые типы)

Передовые системы типов позволяют типам зависеть от значений:

```idris
-- Idris: вектор с длиной, известной в compile-time
data Vect : Nat -> Type -> Type where
    Nil  : Vect 0 a
    (::) : a -> Vect n a -> Vect (n+1) a

-- Конкатенация: тип гарантирует правильную длину
(++) : Vect m a -> Vect n a -> Vect (m+n) a

-- head только для непустых векторов — нельзя вызвать на []!
head : Vect (S n) a -> a
```

Зависимые типы есть в Coq, Agda, Idris. Это позволяет кодировать математические доказательства как программы — верификация аппаратного обеспечения Intel использует Coq.

## 8. Практический выбор

### 8.1 Когда статическая типизация предпочтительна

- Большие кодовые базы (> 100k строк): типы — документация, навигация, безопасный рефакторинг
- Производительность критична: нет overhead на runtime проверки типов
- Команды с частой сменой состава: типы снижают когнитивную нагрузку
- Системное программирование: OS, компиляторы, драйверы

### 8.2 Когда динамическая типизация предпочтительна

- Прототипирование и исследования: меньше boilerplate, быстрый feedback
- Скрипты и автоматизация: короткий срок жизни кода
- Метапрограммирование: динамическое создание структур, декораторы
- DSL и конфигурации: гибкость важнее строгости

### 8.3 Современный тренд: лучшее из обоих

Тренд последнего десятилетия — языки с богатыми системами вывода типов, которые "просто работают" как динамические, но дают гарантии как статические:

- **Rust**: полный вывод типов внутри функций, явные сигнатуры снаружи
- **Kotlin**: null safety + вывод типов, совместимость с Java
- **Swift**: вывод типов + value types для производительности
- **Python + mypy**: постепенная типизация без изменения синтаксиса

## Заключение

Противопоставление статической и динамической типизации устаревает. Вопрос не "какая лучше", а "каков правильный компромисс для конкретной задачи". Статическая типизация даёт производительность, раннее обнаружение ошибок и более безопасный рефакторинг. Динамическая — гибкость, краткость кода, быстрое прототипирование.

Система типов — это инструмент для выражения инвариантов программы. Чем богаче система (дженерики, алгебраические типы, зависимые типы), тем больше инвариантов можно выразить и тем больше ошибок отловит компилятор вместо тестов или пользователей. Но богатство системы типов требует от программиста соответствующего уровня понимания.
