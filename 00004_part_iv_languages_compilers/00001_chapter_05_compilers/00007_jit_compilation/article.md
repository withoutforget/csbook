# JIT-компиляция: V8, JVM, .NET — компилируем в рантайме

JIT-компиляция (Just-In-Time compilation) — это одна из самых элегантных идей в информатике: вместо того чтобы компилировать код заранее или интерпретировать его построчно, система наблюдает за выполнением программы и компилирует наиболее используемые части прямо во время работы, адаптируя оптимизации под реальные данные. Именно благодаря JIT Python-код на PyPy, JavaScript в браузере и Java-приложения достигают производительности, близкой к нативной.

## Что такое JIT и чем он отличается от AOT

Прежде чем погружаться в детали, проясним термины.

**AOT (Ahead-Of-Time compilation)** — компиляция перед запуском. Вы пишете программу на C, запускаете `gcc`, получаете бинарный файл. Этот файл содержит машинный код, готовый к выполнению. Никаких сюрпризов во время работы — всё уже сделано.

**Интерпретация** — противоположная крайность. Интерпретатор читает исходный код (или байт-код) строку за строкой и выполняет каждую инструкцию немедленно. Это гибко и портабельно, но медленно: каждая инструкция требует дополнительной работы интерпретатора по её "пониманию".

**JIT** — компромисс между ними. Программа начинает выполняться интерпретатором или на базовом уровне компиляции, но JIT-компилятор наблюдает за тем, какие части кода выполняются чаще всего (горячие пути, hot paths), и компилирует их в нативный машинный код прямо во время работы.

Аналогия: представьте ресторан. AOT — это готовить всё меню заранее. Интерпретация — готовить каждое блюдо с нуля по заказу. JIT — это понять, что 80% клиентов заказывают пиццу, и наладить конвейер именно для неё.

### Ключевое преимущество JIT перед AOT

JIT знает больше, чем AOT-компилятор! Статический компилятор работает с кодом в вакууме. JIT видит реальные данные:

- Какие типы аргументов реально передаются в функцию
- Какие ветви условных операторов реально выполняются
- Какие виртуальные методы реально вызываются
- Как данные расположены в памяти прямо сейчас

Это позволяет JIT делать агрессивные оптимизации, которые AOT-компилятор не может применить без риска нарушить корректность программы.

## Как работает JVM JIT: C1, C2 и Tiered Compilation

Java Virtual Machine — один из самых изощрённых примеров JIT. Современная JVM (HotSpot) использует многоуровневую компиляцию.

### Уровни компиляции в HotSpot

**Уровень 0 — Интерпретатор.** Новый метод начинает выполняться интерпретатором. Каждая байт-код инструкция декодируется и выполняется. Медленно, но минимальный overhead на старте.

**Уровень 1 — C1 без профилирования.** Быстрый компилятор первого уровня (C1, он же "client compiler") компилирует метод в нативный код без сбора метаданных. Нет инструментации — нет накладных расходов. Применяется для методов, которые вряд ли станут действительно горячими.

**Уровень 2 — C1 с лёгким профилированием.** C1 компилирует с минимальной инструментацией для подсчёта вызовов и итераций циклов.

**Уровень 3 — C1 с полным профилированием.** C1 компилирует с полной инструментацией: типы аргументов, взятые ветви, получатели виртуальных вызовов. Это создаёт накладные расходы, зато собирает точные данные для C2.

**Уровень 4 — C2 (Server compiler).** Агрессивный оптимизирующий компилятор на основе данных профилирования. Генерирует высокооптимизированный нативный код.

```
Новый метод:
    └── Интерпретатор (уровень 0)
            │
            ├── Вызвали N раз? → C1 без профилирования (уровень 1)
            │
            └── Долгий метод? → C1 с профилированием (уровень 3)
                    │
                    └── Достаточно данных? → C2 (уровень 4)
```

### C1: быстрая компиляция

C1 выполняет базовые оптимизации:
- Inlining простых методов
- Устранение мёртвого кода
- Оптимизации циклов (loop unrolling, loop invariant code motion)
- Escape analysis на базовом уровне

C1 работает быстро — компиляция занимает миллисекунды. Это важно: программа не должна "замерзать" при компиляции.

### C2: агрессивная оптимизация

C2 — это промышленный оптимизирующий компилятор. Он основан на алгоритме "Sea of Nodes" (море узлов), где граф зависимостей по данным и потоку управления совмещены в одном представлении.

C2 применяет:

**Inlining** — встраивание вызовов. Самая важная оптимизация. Убирает overhead вызова, открывает возможности для последующих оптимизаций.

```java
// Было:
int result = add(a, b);

// После inlining:
int result = a + b;  // overhead вызова исчез
```

**Escape analysis** — анализ "сбегает" ли объект из метода. Если нет — объект можно разместить на стеке или вообще удалить как абстракцию (scalar replacement):

```java
// Без escape analysis: выделение в куче
Point p = new Point(x, y);
return p.x + p.y;

// После escape analysis: p не "сбегает", можно заменить на поля
return x + y;  // выделения в куче не происходит вообще
```

**Спекулятивные оптимизации** — C2 может предполагать, что виртуальный метод всегда вызывается на объекте одного типа (monomorphic call site), и генерировать прямой вызов вместо виртуального. Если предположение нарушится — происходит deoptimization.

### OSR (On-Stack Replacement)

Что делать, если горячий цикл находится в методе, который уже выполняется? JVM не может остановить выполнение, перекомпилировать метод и продолжить. Для этого существует OSR.

OSR позволяет "на лету" заменить выполняющийся интерпретированный кадр стека скомпилированной версией прямо в середине цикла. Это сложная операция: нужно перенести все локальные переменные из интерпретируемого формата в скомпилированный.

## Как работает V8: Ignition и TurboFan

V8 — JavaScript-движок от Google, используемый в Chrome и Node.js. Его архитектура поучительна тем, что JavaScript — динамически типизированный язык с очень "мягкой" семантикой, и JIT-компиляция здесь особенно важна.

### Ignition: интерпретатор с профилированием

Ignition — это байт-код интерпретатор V8. Когда V8 встречает JavaScript функцию в первый раз:

1. Парсер создаёт AST (Abstract Syntax Tree)
2. Ignition компилирует AST в байт-код — компактное представление
3. Интерпретатор выполняет байт-код, собирая информацию о типах

Ignition устроен как регистровая машина (не стековая). Это даёт компактный байт-код и упрощает анализ для последующей компиляции.

```
Исходный код JS:
function add(a, b) { return a + b; }

Байт-код Ignition (приблизительно):
LdaNamedProperty r0, [0], [4]   // загрузить a
Star r2                          // сохранить в r2  
LdaNamedProperty r0, [1], [6]   // загрузить b
Add r2, [8]                      // сложить
Return
```

### TurboFan: оптимизирующий компилятор

Когда функция вызывается достаточно часто (порог — около 1000 вызовов в V8), она передаётся TurboFan для оптимизации. TurboFan получает байт-код и собранные Ignition профильные данные.

TurboFan работает с представлением "Sea of Nodes" (аналогично C2). Оптимизации включают:

- Специализацию по типам (type specialization)
- Inlining функций
- Устранение проверок типов (если тип известен)
- Vectorization для числовых массивов
- Code motion, constant folding

### Inline Caching: ключевая оптимизация для динамических языков

Inline caching (IC) — критически важная техника для языков с динамической диспетчеризацией.

В JavaScript обращение к свойству объекта `obj.x` теоретически требует поиска в прототипной цепочке каждый раз. Это катастрофически медленно. Inline caching решает это:

**Мономорфный IC (monomorphic):** Если `obj` всегда имеет одну и ту же "форму" (hidden class/Shape), кешируем смещение свойства:

```javascript
// Каждый раз obj имеет форму {x: number, y: number}
function getX(obj) { return obj.x; }

// После IC: вместо поиска — прямой доступ по смещению
// [obj_ptr + offset_of_x]
```

**Полиморфный IC:** Если функция вызывается с 2-4 разными формами, IC хранит несколько вариантов.

**Мегаморфный IC:** Более 4 форм — IC деградирует до обычного поиска.

### Hidden Classes (Shapes/Maps)

V8 присваивает каждому объекту JavaScript "скрытый класс" (hidden class, также называемый Shape в SpiderMonkey или Map в V8-терминологии). Два объекта с одинаковой структурой свойств получают один и тот же скрытый класс.

```javascript
function Point(x, y) {
    this.x = x;  // переход к hidden class C1 (имеет x)
    this.y = y;  // переход к hidden class C2 (имеет x, y)
}

let p1 = new Point(1, 2);  // hidden class C2
let p2 = new Point(3, 4);  // тот же hidden class C2 — IC работает!

// Но:
let p3 = { x: 1 };    // hidden class D1
p3.y = 2;             // hidden class D2 — другой переход!
// p3 и p1/p2 имеют разные hidden classes, хотя содержат x и y
```

### Deoptimization: когда предположения нарушаются

JIT делает предположения (speculative optimizations). Если предположение нарушается — нужен откат.

```javascript
function sum(arr) {
    let s = 0;
    for (let i = 0; i < arr.length; i++) {
        s += arr[i];  // TurboFan предположил: arr содержит только числа
    }
    return s;
}

sum([1, 2, 3, 4]);     // горячий путь — TurboFan оптимизирует
sum([1, 2, "три", 4]); // строка! Deoptimization!
```

При deoptimization:
1. Скомпилированный код бросает "деоптимизирующую ловушку"
2. Восстанавливается интерпретируемое состояние
3. Выполнение продолжается в интерпретаторе
4. Профилирование обновляется — следующая компиляция учтёт строки

Deoptimization — дорогая операция. Важно понимать, когда она происходит.

## Почему цикл с числами в JS быстрый, а с объектами — медленный

Это один из самых важных практических вопросов для JavaScript-разработчиков.

### Числовой массив: оптимальный путь

```javascript
function sumNumbers(arr) {
    let sum = 0;
    for (let i = 0; i < arr.length; i++) {
        sum += arr[i];
    }
    return sum;
}

const data = new Array(1000000).fill(0).map((_, i) => i);
console.time('numbers');
sumNumbers(data);
console.timeEnd('numbers'); // ~1-2ms
```

V8 определяет, что `arr` — это `PACKED_SMI_ELEMENTS` (упакованный массив маленьких целых чисел). TurboFan генерирует код, похожий на C:
- Массив хранится как непрерывный блок памяти с числами типа `int32` или `float64`
- Цикл не требует box/unbox операций
- Возможна SIMD-векторизация

### Объектный массив: много накладных расходов

```javascript
function sumObjects(arr) {
    let sum = 0;
    for (let i = 0; i < arr.length; i++) {
        sum += arr[i].value;  // доступ к свойству!
    }
    return sum;
}

const data = new Array(1000000).fill(null).map((_, i) => ({ value: i }));
console.time('objects');
sumObjects(data);
console.timeEnd('objects'); // ~10-50ms — в 10-20 раз медленнее!
```

Проблемы:
1. `arr[i]` — это указатель на объект в куче
2. `arr[i].value` — разыменование указателя + поиск свойства (хотя IC помогает)
3. Объекты разбросаны по куче → плохая локальность кеша
4. `sum += value` — JavaScript number может быть float64, но нужно unboxing

**Практический урок:** Для числовых вычислений используйте `TypedArray`:

```javascript
const data = new Float64Array(1000000);
for (let i = 0; i < data.length; i++) data[i] = i;

console.time('typed');
let sum = 0;
for (let i = 0; i < data.length; i++) sum += data[i];
console.timeEnd('typed'); // ~0.5ms — ещё быстрее!
```

## Профилирование горячих путей

### Счётчики вызовов и итераций

JIT-системы отслеживают:

1. **Invocation counter** — сколько раз вызвался метод
2. **Back-edge counter** — сколько раз выполнялся обратный переход в цикле

В HotSpot: метод компилируется C1, когда `invocation_count + backedge_count > threshold` (по умолчанию 1500 для C1, 10000+ для C2).

### Что профилируется

**Типы аргументов:** При каждом вызове записывается, с каким типом пришли аргументы. Это основа для type-specialized compilation.

**Ветви:** Какая ветвь if/else берётся чаще? Это позволяет оптимизировать "горячую" ветвь (put it on the fast path) и превратить "холодную" в редкий случай.

**Виртуальные вызовы:** Какой конкретный метод реально вызывается? 80% виртуальных вызовов мономорфны — всегда один тип. Это позволяет devirtualize (заменить виртуальный вызов прямым).

## LLVM в контексте JIT

LLVM (Low Level Virtual Machine) — это не только инструментальная цепочка для статической компиляции. LLVM предоставляет отличную основу для JIT-компиляторов через `llvm::ExecutionEngine` и более современный `MCJIT`/`OrcJIT`.

### LLVM ORC JIT

ORC (On-Request Compilation) — современный JIT-фреймворк в LLVM:

```cpp
// Создание JIT-компилятора на основе LLVM
auto JIT = LLJITBuilder().create();

// Добавление модуля
JIT->addIRModule(ThreadSafeModule(std::move(M), std::move(Ctx)));

// Поиск скомпилированной функции
auto Sym = JIT->lookup("myFunction");
auto *FP = (int(*)(int))Sym->getAddress();

// Вызов скомпилированного кода
int result = FP(42);
```

### Кто использует LLVM для JIT

- **Julia** — каждая функция компилируется LLVM при первом вызове с конкретными типами аргументов. Это позволяет Julia достигать производительности C для числовых вычислений.
- **LLDB** — отладчик использует LLVM JIT для вычисления выражений в отладчике.
- **WebAssembly** — многие движки (Wasmtime через Cranelift, V8) используют JIT для Wasm.
- **Mesa** — компиляция шейдеров OpenGL/Vulkan.

### Cranelift: альтернатива LLVM для JIT

Cranelift — быстрый код-генератор, разработанный для Wasmtime и Firefox. В отличие от LLVM, оптимизирован для скорости компиляции, а не максимального качества кода:

- Компиляция в разы быстрее LLVM
- Код хуже оптимизирован (но достаточно хорош)
- Идеален для JIT, где время компиляции критично

## Warm-up и производительность JIT в продакшене

### Проблема холодного старта

JIT-скомпилированный код быстр только после разогрева. В продакшене это создаёт проблемы:

- Первые запросы к сервису обрабатываются медленно
- После деплоя нового кода — новый разогрев
- Микросервисы с коротким временем жизни не успевают разогреться

### Profile-Guided Optimization (PGO) для JIT

Современные JVM поддерживают сохранение профиля:

```bash
# GraalVM: сохранение профиля в файл
java -XX:+UnlockExperimentalVMOptions \
     -XX:+EnableJVMCI \
     --vm.Dgraal.CompilationFailureAction=Print \
     MyApp

# Затем использование профиля при следующем запуске
```

### GraalVM Native Image: AOT с информацией JIT

GraalVM Native Image компилирует Java в нативный исполняемый файл заранее (AOT), используя анализ замкнутого мира (closed-world assumption). Результат: мгновенный старт без разогрева, но без адаптивных оптимизаций времени выполнения.

## .NET CLR JIT: RyuJIT

.NET использует JIT-компилятор RyuJIT (ранее JIT32/JIT64). Основные характеристики:

### Tiered Compilation в .NET

Аналогично JVM, .NET использует многоуровневую компиляцию:

- **Tier 0** — быстрая компиляция с минимальными оптимизациями (без inlining)
- **Tier 1** — переоптимизация с полным набором оптимизаций

```csharp
// Метод начинает с Tier 0
public static int Sum(int[] arr) {
    int sum = 0;
    for (int i = 0; i < arr.Length; i++) {
        sum += arr[i];  // счётчик инкрементируется
    }
    return sum;
}
// После достаточного количества вызовов — Tier 1 с inlining и векторизацией
```

### PGO в .NET 6+

.NET 6 ввёл Dynamic PGO — аналог профилирования JVM, но с возможностью сохранять и загружать профили между запусками:

```xml
<!-- В .csproj для включения Dynamic PGO -->
<PropertyGroup>
  <TieredPGO>true</TieredPGO>
</PropertyGroup>
```

### SIMD и векторизация в RyuJIT

RyuJIT автоматически векторизует циклы для x86 SSE2/AVX2:

```csharp
// Этот код RyuJIT может автоматически векторизовать
public static void AddArrays(float[] a, float[] b, float[] result) {
    for (int i = 0; i < a.Length; i++) {
        result[i] = a[i] + b[i];
    }
}
// Превращается в инструкции ADDPS (SSE) или VADDPS (AVX2)
```

## Практические советы: помогаем JIT

### Для JavaScript (V8)

1. **Мономорфные call sites:** Передавайте в функцию всегда один тип

```javascript
// Плохо: полиморфный call site
function process(x) { return x * 2; }
process(1);       // number
process("hello"); // string! Deoptimization!

// Хорошо: всегда числа
process(1);
process(2);
```

2. **Не меняйте форму объектов после создания:**

```javascript
// Плохо
const obj = {};
obj.x = 1;       // hidden class 1
obj.y = 2;       // hidden class 2 — переход
obj.z = 3;       // hidden class 3 — ещё переход

// Хорошо
const obj = { x: 1, y: 2, z: 3 };  // один hidden class сразу
```

3. **TypedArray для числовых данных:**

```javascript
// Для числовых вычислений
const buffer = new Float64Array(n);  // гарантированно float64
```

### Для Java (HotSpot)

1. **Избегайте мегаморфных call sites:**

```java
// Если метод implement разными классами — IC станет мегаморфным
interface Shape { double area(); }
// Лучше: ограничить количество реальных реализаций до 2-4
```

2. **Помогайте escape analysis:**

```java
// Плохо: объект "убегает" в коллекцию
List<Point> points = new ArrayList<>();
for (int i = 0; i < n; i++) {
    points.add(new Point(i, i));  // Point уходит в кучу
}

// Лучше: работать с координатами напрямую
int[] xs = new int[n], ys = new int[n];
```

3. **Прогревайте сервис перед нагрузочным тестированием:**

```java
// Прогрев: прогоните критические пути несколько тысяч раз
for (int warmup = 0; warmup < 10000; warmup++) {
    criticalMethod(testData);
}
// Теперь JIT скомпилировал criticalMethod
```

## Трассировочный JIT vs Метод-JIT

Исторически существовало два подхода.

**Метод-JIT (Method JIT):** Компилируется отдельный метод/функция. Это подход JVM и V8. Профилируются методы.

**Трассировочный JIT (Tracing JIT):** Компилируется "горячая трасса" — последовательность инструкций через несколько функций. LuaJIT использовал именно этот подход.

```lua
-- LuaJIT: трасса компилируется через границы функций
local function inner(x) return x + 1 end

for i = 1, 1000000 do
    local x = inner(i)  -- цикл + вызов = одна трасса для JIT
    -- inner inlined прямо в трассу
end
```

LuaJIT — легендарный пример: Lua-код часто быстрее Python в 100 раз благодаря трассировочному JIT.

## Итоги

JIT-компиляция — это мощный инструмент, позволяющий языкам с высокоуровневой семантикой достигать производительности, близкой к нативной. Ключевые идеи:

1. **Многоуровневость:** Быстрый первый уровень + медленная но агрессивная оптимизация на горячих путях
2. **Профилирование:** JIT знает реальные типы и реальные ветви — это основа спекулятивных оптимизаций
3. **Deoptimization:** Гарантия корректности при нарушении предположений
4. **Inline caching:** Ключ к производительности динамических языков
5. **Помогайте JIT:** Пишите предсказуемый код с однородными типами
