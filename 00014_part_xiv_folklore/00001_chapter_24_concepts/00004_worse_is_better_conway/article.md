# Хуже — значит лучше: законы Конвея, Постела, Хайрема и другие принципы CS-фольклора

В Computer Science существует особая категория знания: идеи, которые не доказываются формально и не измеряются экспериментально, но тем не менее оказываются верными раз за разом. Это — фольклор профессии, накопленный опытом поколений программистов.

Некоторые из этих принципов назвали "законами" по имени их авторов. Другие остались безымянными афоризмами. Но все они описывают реальные паттерны: как системы взаимодействуют с людьми, как организации строят программное обеспечение, как компромиссы определяют судьбу технологий.

В этой статье — четыре принципа, которые изменили то, как мы думаем о дизайне систем.

## Worse is Better: как Unix победил MIT

### Происхождение

В 1991 году Ричард Гэбриел (Richard Gabriel), один из ключевых разработчиков Common Lisp, написал эссе "Worse is Better". Он объяснял, почему Unix (который он считал технически уступающим) завоевал мир, а Lisp Machine (технически превосходящая) осталась нишевым продуктом.

Гэбриел описал два подхода к дизайну:

### "Правильный подход" (MIT-стиль, Lisp)

Дизайн ведётся по нескольким критериям:

- **Правильность**: дизайн должен быть корректным во всех аспектах
- **Согласованность**: интерфейс не должен иметь противоречий или исключений  
- **Полнота**: должны поддерживаться все разумные случаи
- **Простота**: важна, но *не важнее трёх предыдущих*

### "Хуже — значит лучше" (Unix/C-стиль, New Jersey)

- **Правильность**: дизайн должен быть корректным во всех аспектах
- **Простота**: важна, *важнее всего остального*
- **Согласованность**: желательна, но при конфликте с простотой — жертвуем согласованностью
- **Полнота**: можно пожертвовать полнотой ради простоты

Разница кажется небольшой, но следствия огромны.

### История с PC Loser-ing Problem

Гэбриел иллюстрирует разницу на примере системного вызова.

**MIT-подход**: если системный вызов прерван из-за аппаратного прерывания в процессе — он должен автоматически перезапуститься, чтобы пользователь не видел прерывания (согласованность интерфейса).

**Unix-подход**: системный вызов возвращает ошибку EINTR. Программист должен сам проверять и перезапускать.

```c
// Unix: обработка EINTR — ответственность программиста
ssize_t n;
do {
    n = read(fd, buf, sizeof(buf));
} while (n == -1 && errno == EINTR);

if (n == -1) {
    perror("read failed");
    exit(1);
}
```

Это "хуже" — программисту нужно думать о EINTR, писать дополнительный код. Зато ядро проще. 

Но вот парадокс: **более простая реализация побеждает более правильную**.

Почему? Гэбриел формулирует ключевой тезис:

> "It is slightly better to be simple than correct."

Простой интерфейс / простая реализация:
- Быстрее портируется на новые платформы
- Легче учится и используется
- Распространяется как вирус — люди начинают использовать сразу
- Позже, когда достигает критической массы — недостатки исправляются

Unix был "достаточно хорошим" сразу. Он мог быть переписан на C и портирован на PDP-11, VAX, затем PC. Lisp Machine требовала специального железа.

### Примеры Worse is Better в современной разработке

**Python vs Haskell**

Python — "хуже": динамическая типизация, медленнее, нет встроенного параллелизма. Haskell — "правильнее": строгая система типов, чистота функций, безопасный параллелизм.

Но Python стал lingua franca для ML/AI, научного программирования, автоматизации — именно потому, что простота входа важнее корректности.

**JavaScript**

JavaScript был создан за 10 дней. Это видно: `null == undefined` (true), `typeof null === "object"` (баг), число с плавающей точкой ($0.1 + 0.2 \neq 0.3$), неявные преобразования типов.

Но JavaScript — единственный язык, встроенный в браузер. Это критическая масса. Теперь на нём строят TypeScript (исправляет баги), Babel (новые фичи в старых браузерах), целую экосистему.

**SQL**

SQL не реляционно-алгебраически чист. В нём есть NULL (трёхзначная логика!), неоднозначные семантики GROUP BY, vendor-специфические расширения. Но SQL — стандарт де-факто уже 50 лет.

**Worse is Better и стартапы**

"Worse is Better" формирует подход к разработке: выпустить "достаточно хорошее" решение быстро, получить реальных пользователей, итерировать.

```python
# MVP: хуже (нет валидации, нет обработки ошибок)
def create_user(email: str, password: str):
    user = {"email": email, "password": hash_password(password)}
    db.insert(user)
    return user

# "Правильная" версия: лучше, но займёт 3 недели
def create_user(
    email: EmailStr,  # Pydantic валидация
    password: SecretStr,
    first_name: str,
    last_name: str,
    timezone: str = "UTC",
    locale: str = "en-US"
) -> UserDTO:
    # Валидация email, проверка уникальности, password policy,
    # welcome email, audit log, GDPR compliance...
    pass
```

Первый вариант можно выпустить сегодня. Второй — может никогда не выйти, если стартап закроется до релиза.

Но Worse is Better — не оправдание технического долга навсегда. Ключ: "достаточно хорошо" → реальное использование → улучшение на основе feedback.

## Закон Конвея

### Формулировка

Мелвин Конвей (Melvin Conway) в 1968 году:

> "Организации, которые проектируют системы, ограничены в своих решениях структурой коммуникации этих организаций."

Проще: **архитектура системы отражает организационную структуру команды**.

### Примеры в реальности

Если над компилятором работают четыре команды — у вас будет четырёхпроходный компилятор.

Если система интеграции разработана командами A, B, C — будет три системы интеграции с API между ними.

```
Организация:          Архитектура системы:
[Team UI]             [Frontend]
    ↕                      ↕
[Team API]     →      [REST API]
    ↕                      ↕
[Team DB]             [Database Layer]
```

Это не мистика. Это коммуникация: команды согласовывают интерфейсы между собой. Горизонтальный API (между командами) возникает там, где горизонтальная граница в организации.

### Inverse Conway Maneuver

Мартин Фаулер и Сэм Ньюман сформулировали обратный манёвр Конвея:

**Если хочешь определённую архитектуру — организуй команды соответствующим образом.**

Amazon в 2002 году: Джефф Безос издал знаменитый мандат. Каждая команда должна предоставлять свои данные и функциональность только через API. Нет другого способа коммуникации.

Результат: Amazon превратилась в платформу. Через несколько лет они запустили AWS — потому что внутренние API-сервисы уже были построены.

```
Хочешь: Микросервисы с четкими границами
Сделай: Маленькие автономные команды ("two-pizza teams")
        Каждая команда владеет своим сервисом end-to-end
        Минимум зависимостей между командами

Хочешь: Монолит с чёткими модулями
Сделай: Одна команда, чёткие code ownership rules
        Запрет прямого обращения к internal модулей других
```

### Team Topologies

Матью Скелтон и Мануэль Паэйс в книге "Team Topologies" (2019) систематизировали Закон Конвея в практическую методологию.

Четыре типа команд:
1. **Stream-aligned**: отвечает за product stream (feature team)
2. **Platform**: создаёт внутреннюю платформу для stream-aligned команд
3. **Enabling**: помогает другим командам (DevOps, Architecture Guild)
4. **Complicated subsystem**: изолированная экспертиза (ML, Payments)

Три взаимодействия:
1. **Collaboration**: тесная работа временно
2. **X-as-a-Service**: одна команда предоставляет сервис другой
3. **Facilitating**: enabling команда помогает другой

```python
# Закон Конвея в коде: если команды разделены "горизонтально" (frontend/backend)
# vs "вертикально" (по продуктовым доменам)

# Горизонтальное разделение → многослойная архитектура
# presentation.py    ← Frontend team
# api.py             ← API team
# service.py         ← Backend team
# repository.py      ← DBA team

# Вертикальное разделение → продуктовые домены (Conway-aligned)
# orders/            ← Orders team (owns все слои)
#   api.py
#   service.py
#   repository.py
# payments/          ← Payments team
#   api.py
#   service.py
#   repository.py
```

Вертикальное разделение → команда может деплоить фичу end-to-end независимо от других.

### Закон Конвея и OpenSource

Закон Конвея работает и для OpenSource. Структура open-source проекта отражает социальную структуру сообщества:
- Linux: Линус Торвальдс → maintainers подсистем → contributors
- Linux kernel архитектура: монолитное ядро с чёткими подсистемами

## Закон Постела (Принцип надёжности)

### Формулировка

Джон Постел (Jon Postel) сформулировал принцип в RFC 793 (TCP, 1981):

> "Be conservative in what you send, be liberal in what you accept."
>
> "Будь консервативен в том, что отправляешь; будь либерален в том, что принимаешь."

Другая формулировка: **Robustness Principle** (Принцип надёжности).

Постел руководствовался практическими соображениями: ранний интернет состоял из разных реализаций протоколов с небольшими отклонениями. Чтобы сеть работала — каждый узел должен был "прощать" небольшие отклонения в полученных данных.

### Позитивная интерпретация

Принцип Постела помог TCP/IP завоевать мир. Разные реализации TCP на разных OS говорили "немного по-разному" — но были достаточно совместимы, чтобы работать вместе.

HTML-браузеры — пример либерализма в приёме. Даже документы с ошибочным HTML (незакрытые теги, неправильная вложенность) отображаются браузером с "best effort". Это позволило вебу распространиться — не нужно было идеально знать HTML.

```python
# Либеральная обработка входных данных

def parse_date(date_str: str) -> datetime:
    """
    Принимаем разные форматы дат (Postel's Law).
    Отдаём всегда в ISO 8601.
    """
    formats = [
        "%Y-%m-%d",          # 2024-01-15
        "%d.%m.%Y",          # 15.01.2024
        "%d/%m/%Y",          # 15/01/2024
        "%B %d, %Y",         # January 15, 2024
        "%Y-%m-%dT%H:%M:%S", # 2024-01-15T14:30:00
    ]
    
    for fmt in formats:
        try:
            return datetime.strptime(date_str.strip(), fmt)
        except ValueError:
            continue
    
    raise ValueError(f"Unrecognized date format: {date_str}")
```

### Критика: закон Постела как источник уязвимостей

В 2019 году Мартин Томсон (главный автор TLS 1.3) написал аргументированную статью против закона Постела:

**Аргумент 1: Либерализм создаёт неоднозначность**

Если A принимает "неправильные" данные от B, то B не узнает, что нарушает спецификацию. Через 10 лет десятки реализаций будут зависеть от этого "неправильного" поведения. Изменить его станет невозможно.

```
Internet Explorer: очень либерален в HTML
→ Сайты писались специально "под IE"
→ Баги IE стали де-факто стандартом
→ Другие браузеры должны были воспроизводить баги IE для совместимости
```

**Аргумент 2: Либерализм создаёт уязвимости безопасности**

Если получатель "прощает" неправильный input — это создаёт векторы атак.

```
HTTP Request Smuggling: разные реализации HTTP по-разному обрабатывают 
неоднозначные запросы (Content-Length vs Transfer-Encoding).
Атакующий отправляет запрос, который proxy видит одним образом,
а бэкенд — другим.
```

**Аргумент 3: Лучше быть строгим с обеих сторон**

Современный подход: **strict parsing + versioning**.

```python
# Строгий API: не принимаем неправильный формат
from pydantic import BaseModel, validator
from datetime import datetime

class CreateOrderRequest(BaseModel):
    user_id: int  # Строгий тип
    items: list[OrderItem]  # Не list, не tuple — именно list[OrderItem]
    scheduled_at: datetime  # ISO 8601, нет вариантов
    
    class Config:
        extra = "forbid"  # Запрещаем неизвестные поля
    
    @validator("items")
    def items_not_empty(cls, v):
        if not v:
            raise ValueError("items cannot be empty")
        return v

# При изменении API — версионирование
# /api/v1/orders — старый формат
# /api/v2/orders — новый формат
# Обе версии работают параллельно
```

**Практический компромисс**: будьте либеральны во *входных* данных для UI (пользователи делают ошибки). Будьте строги во *внутренних* API (разработчики должны знать спецификацию).

## Закон Хайрема

### Формулировка

Хайрем Райт (Hyrum Wright) в своей PhD диссертации (Google, ~2012) и позднее в популярном виде:

> "With a sufficient number of users of an API, it does not matter what you promise in the contract: all observable behaviors of your system will be depended upon by somebody."
>
> "При достаточном числе пользователей API неважно, что написано в контракте: на каждое наблюдаемое поведение системы кто-нибудь будет полагаться."

### Суть

Любое наблюдаемое поведение — даже случайное, даже недокументированное — станет частью неформального контракта для достаточно большого числа пользователей.

```python
# Вы написали функцию, возвращающую список пользователей
def get_users() -> list[User]:
    return db.query("SELECT * FROM users ORDER BY id")

# В документации: "возвращает список пользователей"
# НЕ документировано: порядок сортировки

# Через год:
# 10 000 пользователей API
# 47 из них написали код, предполагающий ORDER BY id
# Какой-то тест проверяет: assert get_users()[0].id < get_users()[1].id

# Вы хотите изменить на ORDER BY created_at для производительности
# Но 47 пользователей сломаются. Закон Хайрема.
```

### Реальные примеры

**Python hash randomization**

До Python 3.3 порядок итерации по словарю был детерминированным (и зависел от реализации). Тысячи программ полагались на этот конкретный порядок. В Python 3.3 добавили рандомизацию хэшей — порядок стал случайным. Много кода сломалось.

**Linux system calls**

Добавить флаг `O_CLOEXEC` в open() казалось простым — это новый необязательный флаг. Но некоторые программы, полагаясь на конкретные значения errno, флаги и поведение граничных случаев, сломались.

Линус Торвальдс известен цитатой: "We do not break userspace." Это прямое следствие Закона Хайрема: нельзя изменить любое наблюдаемое поведение Linux без риска сломать что-то.

**Google API Changes**

Google Search изменил порядок результатов → SEO-инструменты, которые парсили страницы в определённом порядке, сломались. Google не обещал конкретный порядок HTML-элементов — но пользователи на него полагались.

### Импликации для дизайна API

**Семантическое версионирование недостаточно**

SemVer говорит: MAJOR.MINOR.PATCH, breaking changes → MAJOR версия.

Но Закон Хайрема говорит: любое изменение *потенциально breaking*, потому что кто-то мог полагаться на старое поведение.

```python
# Версия 1.0.0
def sort_users(users: list[User]) -> list[User]:
    return sorted(users, key=lambda u: u.name)
    # Побочный эффект: при одинаковом name — сортировка по id
    # НЕ документировано!

# Версия 1.0.1 (PATCH — только исправление бага)
def sort_users(users: list[User]) -> list[User]:
    return sorted(users, key=lambda u: (u.name, u.created_at))
    # Изменили порядок при одинаковом name
    # Формально: PATCH (уточнили "правильную" сортировку)
    # Реально: BREAKING для тех, кто полагался на старый порядок
```

**Как жить с Законом Хайрема**

1. **Документируйте явно "non-guarantees"**: "Порядок возвращаемых элементов не гарантирован"

2. **Тестируйте поведение, не реализацию**: тесты должны проверять контракт, а не конкретный порядок шагов

3. **Deprecation period**: перед удалением функции — период deprecation с warnings

4. **Stability guarantees**: явно указывайте уровень стабильности (alpha/beta/stable/deprecated)

```python
import warnings
from functools import wraps

def deprecated(reason: str, replacement: str = None):
    """Маркер устаревшего API с Hyrum-compatible предупреждением."""
    def decorator(func):
        @wraps(func)
        def wrapper(*args, **kwargs):
            msg = f"{func.__name__} is deprecated: {reason}"
            if replacement:
                msg += f". Use {replacement} instead."
            warnings.warn(msg, DeprecationWarning, stacklevel=2)
            return func(*args, **kwargs)
        return wrapper
    return decorator

@deprecated(
    "sort_users() no longer guarantees stable sort order",
    replacement="sort_users_v2(users, key='name')"
)
def sort_users(users: list) -> list:
    return sorted(users, key=lambda u: u.name)
```

5. **Флаг поведения**: вместо изменения поведения — добавить флаг для нового

```python
def get_users(
    order_by: str = "id",  # Старое поведение (Hyrum's Law compatibility)
    # "created_at" — новый, более эффективный порядок
    # Явный параметр вместо изменения умолчания
) -> list[User]:
    return db.query(f"SELECT * FROM users ORDER BY {order_by}")
```

## Принцип Хостадтера

Дуглас Хостадтер (Douglas Hofstadter) сформулировал в "Gödel, Escher, Bach" (1979):

> "Это всегда занимает больше времени, чем вы ожидаете, даже с учётом Закона Хостадтера."

Самореферентное наблюдение: даже зная этот принцип, вы всё равно недооцениваете время. Это подтверждено исследованиями когнитивных психологов: **planning fallacy** (систематическая недооценка времени на задачи).

```python
# Имплицитный закон Хостадтера в Sprint Planning
estimated_story_points = 8
actual_story_points = 21  # Restrospective

# После нескольких спринтов: velocity ~ 70% от оценки
# Поэтому опытные команды умножают оценки на коэффициент
velocity_factor = 0.7
realistic_estimate = estimated_story_points / velocity_factor
```

## Закон Паркинсона и программирование

Сирил Паркинсон (Cyril Northcote Parkinson) в 1955:

> "Работа расширяется, заполняя всё время, отведённое на её выполнение."

В программировании это проявляется:
- Рефакторинг может продолжаться бесконечно
- Оптимизация — тоже
- "Пока баг не закрыт — можно добавить ещё одно улучшение"

```python
# Парадокс Паркинсона в code review

# Без дедлайна:
# "Можно ещё улучшить имена переменных... 
#  и добавить типы... 
#  и оптимизировать SQL... 
#  и написать дополнительные тесты..."

# С deadline (релиз через час):
# "Работает? Тесты зелёные? Merge!"

# Оба подхода неоптимальны.
# Решение: явный Definition of Done
```

## Правило 90-90

Том Каргилл (Tom Cargill, Bell Labs):

> "Первые 90% кода занимают первые 90% времени разработки. Оставшиеся 10% кода занимают оставшиеся 90% времени."

Описывает нелинейность разработки: последние 10% (edge cases, обработка ошибок, производительность, безопасность) стоят столько же, сколько первые 90%.

```
Функциональность | 90%   | Готово!
Edge cases        | +5%   | Хм, почти...
Обработка ошибок  | +3%   | Почти готово!
Безопасность      | +1%   | Последние штрихи!
Производительность| +0.5% | Финальная полировка!
Документация      | +0.5% | Практически там!
```

## Бритва Оккама в программировании

Уильям Оккамский (14 век):

> "Не следует множить сущности без необходимости."

В программировании: **не добавляй сложности без реальной необходимости**. Простейшее решение, которое работает — лучшее.

```python
# Нарушение Бритвы Оккама (over-engineering)
class AbstractUserFactoryInterface:
    pass

class ConcreteUserFactory(AbstractUserFactoryInterface):
    def create_user(self, data: dict) -> 'AbstractUser':
        pass

class AbstractUser:
    pass

class ConcreteUser(AbstractUser):
    pass

# Когда достаточно:
@dataclass
class User:
    id: int
    name: str
    email: str
```

Современное воплощение: **YAGNI** (You Aren't Gonna Need It) из Extreme Programming. Не реализуй функциональность "на будущее" — это будущее может никогда не наступить.

## Объединяющая тема: компромисс везде

Все эти принципы — о компромиссах:

| Принцип | Компромисс |
|---------|-----------|
| Worse is Better | Правильность vs Распространённость |
| Закон Конвея | Архитектура системы vs Архитектура организации |
| Закон Постела | Совместимость vs Безопасность/Строгость |
| Закон Хайрема | Гибкость API vs Стабильность контракта |
| Закон Хостадтера | Оптимизм vs Реализм планирования |

Нет "правильного" выбора в вакууме. Есть правильный выбор в контексте: масштаба системы, числа пользователей, скорости изменений, требований безопасности.

Знание этих принципов не даёт готовых ответов — но помогает задавать правильные вопросы.
