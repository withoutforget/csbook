# NTP: как компьютеры синхронизируют часы по сети

Представьте оркестр без дирижёра: каждый музыкант играет в своём темпе, и вместо симфонии получается какофония. Именно так выглядели бы компьютерные сети без синхронизации времени. TLS-сертификаты бы не валидировались, Kerberos-аутентификация бы ломалась, распределённые транзакции бы конфликтовали, а логи было бы невозможно сопоставить. Network Time Protocol (NTP) — это «дирижёр» интернета, удерживающий все часы в согласованном такте.

## Зачем синхронизировать время

Прежде чем разбирать механику NTP, важно понять, почему синхронизация критична:

### TLS/SSL сертификаты

Каждый сертификат содержит поля `Not Before` и `Not After`. Если системные часы сервера или клиента сильно расходятся с реальным временем, валидация сертификата провалится:

```
SSL_ERROR_EXPIRED_CERT_ALERT — сертификат просрочен с точки зрения сервера
SSL_ERROR_BAD_CERT_ALERT — сертификат ещё не действителен с точки зрения клиента
```

При расхождении часов более чем на несколько минут HTTPS-соединения начнут падать.

### Kerberos аутентификация

Kerberos — протокол аутентификации в корпоративных сетях (Active Directory). Он принципиально требует синхронизации часов: по умолчанию допуск составляет $\pm 5$ минут. При большем расхождении аутентификация отклоняется с ошибкой `KRB_AP_ERR_SKEW` (clock skew too great).

Это предотвращает атаки повторного воспроизведения (replay attacks): злоумышленник, перехвативший токен аутентификации, не может использовать его позже.

### Распределённые базы данных

В системах вроде Cassandra, CockroachDB, Google Spanner временные метки используются для упорядочивания операций. Расхождение часов между узлами может привести к нарушению причинно-следственных отношений: событие B, которое произошло после события A, получит меньшую временну́ю метку.

### Логирование и debugging

При расследовании инцидентов необходимо сопоставлять логи с разных серверов. Расхождение часов на несколько секунд делает эту задачу крайне сложной.

## Иерархия стратумов (stratum)

NTP организует серверы в иерархию уровней, называемых стратумами (stratum):

```
Stratum 0: Атомные часы, GPS-приёмники (не в сети, напрямую)
              ↓
Stratum 1: Серверы, подключённые к Stratum 0 напрямую
              ↓
Stratum 2: Серверы, синхронизирующиеся с Stratum 1
              ↓
Stratum 3: Серверы, синхронизирующиеся с Stratum 2
              ↓
              ... (до Stratum 15)
Stratum 16: Несинхронизированный (не используется)
```

**Stratum 0** — это аппаратные эталоны: атомные часы (цезиевые, рубидиевые), GPS-приёмники, радиоприёмники WWVB. Они подключены не по сети, а напрямую к Stratum-1 серверам через последовательный порт или специальные интерфейсы.

**Stratum 1** — основа интернет-инфраструктуры NTP. Публичные Stratum-1 серверы содержат организации вроде NIST, PTB (Германия), NPL (Великобритания), а также многие университеты и технологические компании.

```bash
# Популярные NTP-серверы
pool.ntp.org          # Пул NTP-серверов
time.cloudflare.com   # Cloudflare (Stratum 3)
time.google.com       # Google (использует собственную инфраструктуру)
ntp1.vniiftri.ru      # ВНИИФТРИ (Россия, Stratum 1)
```

На практике большинство серверов синхронизируются с Stratum 2-3, что обеспечивает точность в пределах единиц-десятков миллисекунд.

## Алгоритм NTP: четыре временны́е метки

Ключевая математика NTP проста, но элегантна. Для вычисления смещения часов и задержки сети используются четыре временны́е метки:

```
Клиент                    Сервер
  |                          |
  |  запрос (T1)             |
  |------------------------->|
  |                     (T2) | получение запроса
  |                     (T3) | отправка ответа  
  |  ответ (T4)              |
  |<-------------------------|
```

- **T1**: время отправки запроса (клиентские часы)
- **T2**: время получения запроса (серверные часы)
- **T3**: время отправки ответа (серверные часы)
- **T4**: время получения ответа (клиентские часы)

### Вычисление задержки и смещения

```
Задержка сети (round-trip delay):
δ = (T4 - T1) - (T3 - T2)

Смещение часов (clock offset):
θ = ((T2 - T1) + (T3 - T4)) / 2
```

Пример:
```
T1 = 100.000  (клиент отправил запрос)
T2 = 100.020  (сервер получил запрос, его часы опережают на ~16 мс)
T3 = 100.025  (сервер отправил ответ)
T4 = 100.045  (клиент получил ответ)

δ = (100.045 - 100.000) - (100.025 - 100.020) = 0.045 - 0.005 = 0.040 с = 40 мс
θ = ((100.020 - 100.000) + (100.025 - 100.045)) / 2 = (0.020 - 0.020) / 2 = 0.000 с
```

В данном примере задержка 40 мс, а смещение нулевое — часы клиента и сервера совпадают.

Реальный пример с расхождением:
```
T1 = 1000.000
T2 = 1000.030  (сервер получил через 30 мс, но его часы показывают +10 мс к клиенту)
T3 = 1000.040
T4 = 1000.060

δ = (1000.060 - 1000.000) - (1000.040 - 1000.030) = 0.060 - 0.010 = 0.050 с
θ = ((1000.030 - 1000.000) + (1000.040 - 1000.060)) / 2 = (0.030 - 0.020) / 2 = 0.005 с
```

Смещение $\theta = 5$ мс — часы клиента отстают на 5 мс от сервера.

### Предположение симметричности задержки

NTP предполагает, что время прохождения пакета туда и обратно одинаково ($\delta/2$ в каждую сторону). На практике это не всегда так — асимметрия маршрутов вносит погрешность. Это фундаментальное ограничение NTP по сравнению с более точными протоколами.

## Clock Filter и Clock Discipline

NTP не просто берёт один замер — он собирает статистику и отфильтровывает выбросы.

### Clock Filter Algorithm

Для каждого сервера NTP хранит историю последних 8 замеров. Из них выбирается лучший — с наименьшим дисперсией задержек:

```
Пакет 1: offset=5.3ms, delay=42ms
Пакет 2: offset=5.1ms, delay=38ms   ← выбирается
Пакет 3: offset=5.8ms, delay=55ms
Пакет 4: offset=4.9ms, delay=39ms
...
```

### Clock Discipline Algorithm (PLL/FLL)

Получив оценку смещения $\theta$, NTP не прыгает сразу к правильному времени (это могло бы нарушить монотонность). Вместо этого применяется алгоритм дисциплинирования часов:

- При малом смещении (< 128 мс): **слинг** (slewing) — постепенная корректировка скорости часов (до $\pm 500$ ppm, то есть 0.05%)
- При большом смещении (> 128 мс): возможен **прыжок** (stepping) — мгновенная корректировка

```bash
# Настройки ntpd: разрешить прыжок при старте
tinker stepout 3
tinker panic 0  # не паниковать при больших расхождениях (осторожно!)
```

При slewing часы постепенно ускоряются или замедляются, сходясь к правильному значению. Это занимает время (при смещении 100 мс — около 3 минут при скорости коррекции 500 мкс/с).

## PTP: точнее NTP для финансов и 5G

IEEE 1588 Precision Time Protocol (PTP) — следующий уровень точности после NTP. Если NTP даёт точность в единицы миллисекунд, PTP обеспечивает наносекундную точность в локальных сетях.

### Как PTP достигает точности

1. **Hardware timestamping**: временны́е метки ставятся на уровне сетевого оборудования, не ОС, что исключает задержки программного стека (kernel jitter).

2. **Boundary/Transparent Clocks**: специализированные коммутаторы компенсируют задержку внутри самих себя.

3. **Grandmaster Clock**: источник точного времени в PTP-домене (обычно GPS-приёмник).

```
[GPS] → [Grandmaster] → [Boundary Clock] → [Ordinary Clock] → сервер
         Stratum 0         коммутатор           NIC
```

### Применение PTP

- **Финансовые биржи**: MiFID II требует точности временны́х меток до 100 мкс для высокочастотной торговли (HFT)
- **5G сети**: синхронизация радиостанций требует точности до 1-3 мкс
- **Телекоммуникации**: синхронизация между базовыми станциями
- **Промышленные системы**: автоматизация производства

```bash
# Установка PTP в Linux
apt-get install linuxptp

# Запуск ptp4l (PTP для Linux)
ptp4l -i eth0 -m -s

# Синхронизация системных часов через phc2sys
phc2sys -a -rr
```

## Chrony vs ntpd: современный выбор

Исторически ntpd был стандартной реализацией NTP. Сегодня большинство дистрибутивов Linux по умолчанию используют Chrony.

### Преимущества Chrony

```
ntpd: медленно конвергирует, не работает при нестабильной сети
chrony: быстрее конвергирует, лучше при прерывистом подключении
```

Chrony лучше справляется с:
- Виртуальными машинами (где часы нестабильны)
- Ноутбуками (периодически засыпающими)
- Нестабильными WAN-соединениями

```bash
# /etc/chrony.conf
server ntp1.vniiftri.ru iburst
server 0.pool.ntp.org iburst
server 1.pool.ntp.org iburst
server 2.pool.ntp.org iburst

# Stratum при отсутствии синхронизации
local stratum 10

# Минимальные источники для доверия
minsources 2

# Ограничение slew rate
maxdistance 1.5
```

```bash
# Статус chrony
chronyc tracking
chronyc sources -v
chronyc sourcestats

# Пример вывода
Reference ID    : D4567890 (ntp1.vniiftri.ru)
Stratum         : 2
Ref time (UTC)  : Mon May  6 15:30:00 2024
System time     : 0.000012345 seconds slow of NTP time
RMS offset      : 0.000045678 seconds
Frequency       : +23.456 ppm fast
```

### ntpd конфигурация (классика)

```bash
# /etc/ntp.conf
server 0.pool.ntp.org iburst
server 1.pool.ntp.org iburst
server 2.pool.ntp.org iburst
server 3.pool.ntp.org iburst

# Локальный эталон (Stratum 10) при потере связи
server 127.127.1.0
fudge 127.127.1.0 stratum 10

# Дрейф
driftfile /var/lib/ntp/ntp.drift

# Разрешить запросы от локальной сети
restrict 192.168.1.0 mask 255.255.255.0 nomodify notrap
```

## GPS как источник точного времени

GPS (Global Positioning System) — не только навигация. GPS-спутники несут атомные часы (каждый спутник содержит несколько цезиевых и рубидиевых часов). Принимающее оборудование, синхронизируя сигналы от нескольких спутников, получает точное время с погрешностью в наносекунды.

```
GPS-антенна → GPS-приёмник → PPS-сигнал (1 импульс в секунду)
                                   ↓
                          NTP/PTP сервер Stratum 0/1
```

PPS (Pulse Per Second) — электрический импульс, генерируемый GPS-приёмником ровно в начале каждой секунды. Это самый точный способ синхронизировать компьютерные часы.

```bash
# Пример конфигурации ntpd с GPS + PPS
# GPS через NMEA (Stratum 0)
server 127.127.20.0 mode 16 minpoll 4 maxpoll 4
fudge  127.127.20.0 flag1 1 time1 0.105 stratum 1 refid GPS

# PPS (Stratum 0)
server 127.127.22.0 minpoll 4 maxpoll 4
fudge  127.127.22.0 stratum 0 refid PPS
```

## Roughtime: безопасный NTP

Стандартный NTP не обеспечивает криптографической аутентификации: злоумышленник на пути пакетов (MITM) может подделать временну́ю метку. Это известно как NTP amplification attack или атака на время.

Roughtime — протокол, разработанный Adam Langley в Google (2016), обеспечивающий аутентичность времени:

1. Клиент отправляет запрос с **nonce** (случайным числом)
2. Сервер отвечает текущим временем + подписывает ответ + включает nonce клиента
3. Клиент проверяет подпись; nonce предотвращает replay-атаки
4. При спорных случаях клиент может запросить несколько серверов и **доказать мошенничество одного из них** третьей стороне

```
Roughtime RFC draft: https://roughtime.googlesource.com/roughtime
```

В отличие от NTP, Roughtime не претендует на высокую точность (единицы секунд), но гарантирует **аутентичность** — никто не мог подделать ответ.

## Проблема: что делать при большом расхождении

Когда ntpd или chrony обнаруживает большое расхождение (более 1000 секунд по умолчанию в ntpd), возникает «паника»:

```
ntpd: panic: clock is too different from server (>1000s)
```

Это защита от случайного сброса часов. При первом запуске NTP:

```bash
# Принудительная синхронизация (может прыгнуть время)
ntpdate -b pool.ntp.org   # устаревший способ
chronyc makestep          # современный способ

# Или при старте ntpd
ntpd -g  # разрешить большой начальный прыжок
```

### Slewing vs Stepping

| | Slewing | Stepping |
|---|---|---|
| Что это | Постепенное ускорение/замедление | Мгновенный прыжок |
| Монотонность | Сохраняется | Нарушается |
| Скорость | Медленно (~0.5ms/s) | Мгновенно |
| Когда применять | Малые расхождения (< 128 мс) | Большие расхождения, запуск |
| Риски | Долгая конвергенция | Двойные временны́е метки, баги в логах |

Для большинства систем slewing предпочтительнее, так как гарантирует монотонность. Но при первоначальном запуске системы stepping неизбежен.

## Мониторинг и диагностика

```bash
# ntpq — диагностика ntpd
ntpq -p
#      remote           refid      st t when poll reach   delay   offset  jitter
# ===========================================================================
# *ntp1.example.com .GPS.         1 u   42   64  377    5.123    0.013   0.987
# +ntp2.example.com 192.168.1.1   2 u   61   64  377   15.234   -0.102   1.234

# Условные обозначения:
# * — текущий основной источник
# + — приемлемые источники (peer mode)
# x — отклонённый источником (falseticker)
# - — отклонённый алгоритмом (outlier)

# chronyc — диагностика chronyd
chronyc tracking    # текущее состояние
chronyc sources -v  # источники времени
chronyc ntpdata     # детальная статистика по каждому серверу

# timedatectl (systemd)
timedatectl status
# Local time: Mon 2024-05-06 18:30:00 MSK
# Universal time: Mon 2024-05-06 15:30:00 UTC
# RTC time: Mon 2024-05-06 15:30:00
# Time zone: Europe/Moscow (MSK, +0300)
# System clock synchronized: yes
# NTP service: active
```

## Практические рекомендации

### Для серверов в продакшн

```bash
# Всегда используйте несколько источников NTP (минимум 3-4)
# для защиты от "falseticker" (сервер, показывающий неправильное время)
server 0.pool.ntp.org iburst
server 1.pool.ntp.org iburst
server 2.pool.ntp.org iburst
server 3.pool.ntp.org iburst

# Используйте geo-специфичные пулы для меньшей задержки
server 0.ru.pool.ntp.org iburst
```

### Для виртуальных машин

Виртуальные машины имеют особую проблему: при миграции VM между хостами или при резюмировании из спящего режима часы могут сильно сбиться. Рекомендации:

```bash
# В chrony.conf для VM
# Разрешить больший шаг
makestep 1.0 3   # прыжок до 1с разрешён в первые 3 обновления
# или
makestep 1.0 -1  # прыжок всегда разрешён (для нестабильных окружений)
```

### Для AWS/GCP/Azure

Облачные провайдеры предоставляют собственные NTP-серверы:

```bash
# AWS: Amazon Time Sync Service
server 169.254.169.123 prefer iburst    # IPv4
server fd00:ec2::123 prefer iburst      # IPv6 (в VPC)

# GCP
server 169.254.169.254 prefer iburst

# Azure
server time.windows.com iburst
```

Эти серверы работают по локальной сети и имеют меньшую задержку, чем внешние пулы.

## Итог

NTP — незаметная, но критически важная инфраструктура интернета. Основные тезисы:

1. **Стратумы** организуют иерархию точности: Stratum 0 (атомные часы/GPS) → Stratum 1 → Stratum 2 → ...
2. **Четыре временны́е метки** T1-T4 позволяют вычислить смещение и задержку
3. **Slewing** предпочтительнее stepping для поддержания монотонности
4. **PTP (IEEE 1588)** обеспечивает наносекундную точность для финансов и 5G
5. **Chrony** — современный выбор для Linux; лучше работает на нестабильных системах
6. **Roughtime** добавляет криптографическую аутентификацию времени
7. Всегда используйте минимум 4 источника NTP, мониторьте отклонение
