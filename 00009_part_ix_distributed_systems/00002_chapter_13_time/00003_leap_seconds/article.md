# Високосные секунды: почему Google их «размазывает»

В 23:59:59 UTC 30 июня 2012 года произошло нечто необычное: на долю секунды в мире появилось время 23:59:60. Не 00:00:00 следующего дня, а именно 23:59:60. Через секунду часы перешли на 00:00:00 1 июля. Эта лишняя секунда — «високосная секунда» — вызвала глобальный технический сбой. Reddit упал. Mozilla упала. LinkedIn упала. Ядро Linux застряло в бесконечном цикле. Это был один из самых дорогостоящих часовых событий в истории интернета. В этой статье мы разберём, что такое високосные секунды, почему они существуют, и как технологические гиганты научились с ними жить.

## Почему существуют високосные секунды

Проблема фундаментальна: Земля вращается неравномерно.

### Астрономическое vs атомное время

Астрономическая секунда исторически определялась как 1/86400 солнечных суток. Но солнечные сутки непостоянны. На скорость вращения Земли влияют:

- **Приливное торможение**: Луна замедляет Землю через океанские приливы
- **Движение ледников и айсбергов**: таяние полярных льдов перераспределяет массу
- **Сейсмические события**: крупные землетрясения влияют на момент инерции
- **Движение расплавленного ядра**: внутренняя динамика планеты

С 1820 года (когда длина суток составляла ровно 86400 атомных секунд) Земля замедлилась: сутки теперь длятся на несколько миллисекунд дольше, чем 86400 секунд.

Если бы мы игнорировали это расхождение, то через столетия астрономический полдень (Солнце в зените) и UTC-полдень расходились бы на минуты, а через тысячелетия — на часы.

```
Длина суток (в миллисекундах сверх 86400 с):
2020: +0.4 мс/сут
2019: -0.1 мс/сут (Земля ускорилась!)
2015: +1.0 мс/сут
2000: +0.8 мс/сут

Накопленная разница UTC - UT1 (астрономическое время):
не должна превышать ±0.9 секунды
```

Международная служба вращения Земли (IERS, International Earth Rotation and Reference Systems Service) следит за расхождением UTC и UT1. Когда оно приближается к 0.9 секунды, IERS объявляет о добавлении (или теоретически вычитании) секунды.

### Как объявляются високосные секунды

IERS публикует бюллетени (IERS Bulletin C) за 6 месяцев до события. Секунды добавляются только в конце июня или декабря:

```
Дата объявления: 1 января 2016
Событие: добавить секунду 31 декабря 2016, 23:59:60 UTC
Бюллетень: IERS Bulletin C 52
```

За всю историю (с 1972 года по 2016 год) было добавлено 27 секунд. Начиная с 2017 года — ни одной (Земля немного ускорилась). По состоянию на 2024 год общее количество — 37 секунд.

Перечень всех историческх високосных секунд:
```
1972: +1 (июнь), +1 (декабрь)
1973: +1 (декабрь)
...
2016: +1 (декабрь)  — последняя на данный момент
```

## Как выглядит 23:59:60

В обычный день переход полночи выглядит так:
```
23:59:58
23:59:59
00:00:00  ← следующий день
```

В день с положительной високосной секундой:
```
23:59:58 UTC
23:59:59 UTC
23:59:60 UTC  ← ЭТА СЕКУНДА НЕ СУЩЕСТВУЕТ В ОБЫЧНЫЙ ДЕНЬ
00:00:00 UTC  ← новый день
```

Теоретически возможна и отрицательная секунда (пропустить 23:59:59), но это никогда не происходило.

### Unix time и високосные секунды

Здесь начинается головная боль. POSIX (стандарт Unix) определяет сутки как ровно 86400 секунд. По POSIX, последние три секунды дня с високосной секундой выглядят так:

```
23:59:58 UTC = Unix timestamp 1341100798
23:59:59 UTC = Unix timestamp 1341100799
23:59:60 UTC = ??? (POSIX не знает об этом!)
00:00:00 UTC = Unix timestamp 1341100800
```

POSIX просто игнорирует проблему: в полночь Unix timestamp увеличивается на 1 как обычно. Это означает, что **23:59:60 и 00:00:00 имеют одинаковый Unix timestamp** в классической POSIX-реализации — или точнее, высокосная секунда удваивает метку:

```
23:59:58 → 1341100798
23:59:59 → 1341100799  ← одна секунда
23:59:59 → 1341100799  ← та же метка! (двойная 23:59:59)
00:00:00 → 1341100800
```

Это создаёт неопределённость: если в базе данных есть две записи с одинаковым timestamp, какая из них "правильная"?

## Реальные катастрофы

### Linux kernel bug 2012

30 июня 2012 года, когда добавили високосную секунду, в Linux ядрах 2.6.26 и 3.x обнаружился баг. Подсистема hrtimer (high-resolution timers) не была рассчитана на секунду с номером 60. Это вызвало состояние гонки (race condition) в планировщике, которое приводило к 100% загрузке CPU — бесконечному вращению ядра в цикле.

```c
// Упрощённая суть бага:
// ядро ждало "следующей секунды" используя sleep,
// но 23:59:60 не "следующая секунда" в нормальном смысле,
// и таймер срабатывал повторно, входя в цикл
```

**Пострадавшие**: Reddit, Gawker, LinkedIn, Foursquare, Yelp, StumbleUpon, Qantas airlines (системы бронирования).

**Решение**: обновление ядра; временный обходной путь — `date -s "$(date)"` (принудительная установка системного времени).

### Cloudflare bug 2017

В 2017 году Cloudflare обнаружила баг в своей реализации NTP-based time. Когда часы чуть "пошли назад" из-за NTP-коррекции в момент высокосной секунды, код вычислял отрицательную задержку:

```go
// Упрощённая версия бага в коде на Go
start := time.Now()
// ... работа ...
end := time.Now()
elapsed := end.Sub(start)  // ОТРИЦАТЕЛЬНОЕ ЗНАЧЕНИЕ!
```

Go до версии 1.9 использовал wall clock для `time.Now()`, который мог идти назад при NTP-коррекции. Это вызвало панику в части DNS-резолверов Cloudflare — они начали возвращать SERVFAIL вместо обычных ответов.

**Урок**: для измерения интервалов всегда нужно использовать монотонные часы (более подробно — в следующей статье о monotonic vs wall clock).

### Java и 2012

Java Runtime Environment имела аналогичную проблему в 2012 году. Баг был в `java.util.concurrent.ScheduledThreadPoolExecutor`: задачи, запланированные через наносекунды, не выполнялись в ожидаемое время из-за неправильной обработки перехода через секунду 60.

## Что делает Unix time при високосной секунде

Поведение Unix time при високосной секунде зависит от реализации ядра и конфигурации NTP:

### Вариант 1: Двойная секунда (классическое поведение)

```
23:59:58.0 → 1341100798.0
23:59:59.0 → 1341100799.0
23:59:59.5 → 1341100799.5  ← ФАКТИЧЕСКИ 23:59:60.5
00:00:00.0 → 1341100800.0
```

Unix timestamp 1341100799 длится 2 реальные секунды. Это означает, что в течение секунды Unix-часы "стоят на месте".

### Вариант 2: Kernel leap second flag

Современные Linux ядра знают о высокосной секунде (через adjtimex syscall). Когда NTP сообщает о предстоящей второсной секунде, ядро устанавливает флаг `TIME_OOP` (out-of-phase). В момент секунды 60 ядро возвращает `tv_sec = 23:59:60`. Это корректное поведение, но большинство прикладных программ не готово к числу 60 в секундах.

### Вариант 3: Leap Second Smear (Google/Amazon подход)

Это самое элегантное решение, которое мы рассмотрим детально.

## Google Leap Smear: размазывание по 24 часам

Google разработала технику Leap Second Smear в 2011 году. Идея проста: вместо добавления одной секунды в полночь, постепенно **замедлить** серверные часы на протяжении 24 часов так, чтобы суммарная разница составила ровно одну секунду.

### Механика размазывания

```
За 12 часов до полуночи:
  - Серверные часы начинают отставать от UTC на 1/86400 секунды каждую секунду
  
В полночь:
  - Сервер думает, что время = 00:00:00 UTC (нет секунды 23:59:60)
  - Но фактически это примерно 23:59:59.5 UTC
  
12 часов после полуночи:
  - Отставание ликвидировано
  - Сервер снова в синхронизации с UTC
```

Математически: высокосная секунда добавляется к 86400 × 2 = 172800 секундам (24 часа), поэтому каждая секунда "растягивается" в 172801/172800 ≈ 1.0000057870 раза.

```python
# Упрощённая логика Leap Smear
SMEAR_DURATION = 24 * 3600  # секунды
LEAP_SECOND_VALUE = 1  # добавляемая секунда

smear_rate = LEAP_SECOND_VALUE / SMEAR_DURATION
# = 1/86400 ≈ 0.0000115740 секунды в секунду
# = 11.574 микросекунд на секунду

# Во время смазывания: каждая UTC-секунда на сервере
# длится на 11.574 мкс дольше реальной
```

### Почему это работает

Плюсы Leap Smear:
1. **Монотонность**: Unix timestamp никогда не повторяется и не прыгает назад
2. **Нет специального кода**: приложения не знают, что ничего особенного не происходит
3. **Единый подход**: весь кластер Google синхронизируется через внутреннее время Google

Минусы:
1. **Не настоящее UTC**: в течение 24 часов Google-серверы показывают не стандартное UTC
2. **Проблема взаимодействия**: если Google-сервер общается с не-Google-сервером в период смазывания, возможны несоответствия

Google использует собственные атомные часы и Stratum 1 серверы в датацентрах, поэтому может позволить себе управлять временем независимо.

### Amazon (AWS) тоже смазывает

Amazon использует аналогичный подход, но с 24-часовым окном:

```
Amazon Time Sync Service: использует "smear" при добавлении/удалении секунды
Результат: клиенты Amazon Time Sync Service никогда не видят секунду 60
```

Это задокументировано в AWS User Guide. Если вы используете NTP-сервер Amazon (169.254.169.123), ваши EC2-инстансы автоматически получают "смазанное" время.

## POSIX и стандартизация проблемы

Позиция POSIX проблематична по нескольким причинам:

### Двойная интерпретация

```
# Сценарий: добавить секунду 2016-12-31 23:59:60

# NTP-источник сообщает: СЕЙЧАС 2016-12-31 23:59:60
# ОС получает информацию через TAI-UTC разницу

# Но POSIX timestamp для 2017-01-01 00:00:00 = 1483228800
# А для 2016-12-31 23:59:59 = 1483228799
# 2016-12-31 23:59:60 должна быть = 1483228799... но с пометкой?
```

POSIX.1 (2017 revision) признаёт проблему и оставляет поведение системы "implementation defined" при работе с секундой 60.

### TAI как альтернатива

Некоторые системы используют TAI (International Atomic Time) вместо UTC. TAI не имеет секунды 60 — это линейная шкала без коррекций. TAI-UTC = 37 секунд на 2024 год.

```python
# TAI timestamp в Python (используя leapseconds)
import datetime

# Для точных расчётов TAI нужна таблица високосных секунд
# https://hpiers.obspm.fr/iers/bul/bulc/Leap_Second.dat

def tai_to_utc(tai_ts, leap_seconds=37):
    """Конвертация TAI в UTC timestamp"""
    return tai_ts - leap_seconds
```

## Предложение отменить високосные секунды

На Всемирной конференции по радиосвязи ITU-R (WRC-23) в 2023 году было принято историческое решение: **отменить высокосные секунды к 2035 году**.

### Аргументы за отмену

1. **Технологические риски**: каждая высокосная секунда — потенциальный системный сбой
2. **Автоматизация**: в 1970-е годы это корректировалось вручную операторами; сейчас миллионы систем работают автоматически
3. **Редкость**: расхождение UTC и UT1 составляет менее секунды в год; к 2100 году накопится ~1 минута — несущественно для большинства систем
4. **Проблема синхронизации**: разные реализации NTP обрабатывают высокосные секунды по-разному

### Аргументы против отмены

1. **Астрономия и навигация**: требуют привязки к реальному вращению Земли
2. **Традиция**: времясчисление всегда было связано с астрономией
3. **Неопределённое будущее**: через 100-200 лет разница UTC и астрономического времени превысит минуту

### Компромисс 2023

Решение WRC-23: увеличить допустимое отклонение UTC от UT1 до 1 минуты (вместо нынешних 0.9 секунды). Это означает, что очередная высокосная секунда не понадобится примерно до 2135 года, а формально высокосные секунды остаются возможными.

## Практические советы для разработчиков

### Совет 1: Проверьте своё окружение

```bash
# Как работает ваша система с высокосными секундами?
# Узнайте версию ядра и конфигурацию NTP
uname -r
chronyc tracking | grep "Leap status"
# "Leap status     : Normal"  — нет предстоящей высокосной секунды
# "Leap status     : Insert"  — будет добавлена секунда
# "Leap status     : Delete"  — будет удалена секунда (никогда не было)

# Через adjtimex:
python3 -c "import ctypes; print(ctypes.cdll.LoadLibrary(None).adjtimex)"
```

### Совет 2: Используйте монотонный таймер для интервалов

```python
import time

# НЕПРАВИЛЬНО: wall clock для измерения интервалов
start = time.time()
do_work()
elapsed = time.time() - start  # может стать отрицательным в момент секунды!

# ПРАВИЛЬНО: монотонный таймер
start = time.monotonic()
do_work()
elapsed = time.monotonic() - start  # всегда >= 0
```

### Совет 3: Тестирование на высокосные секунды

```bash
# libfaketime позволяет симулировать высокосную секунду
# https://github.com/wolfcw/libfaketime

# Симуляция: начинаем в 23:59:58
FAKETIME="2016-12-31 23:59:58" ./my_program

# Или через Docker
docker run --env FAKETIME="2016-12-31 23:59:58" myimage
```

### Совет 4: Если вы облачный пользователь AWS/GCP

Вы уже защищены — облачные провайдеры используют smear. Но если ваш код взаимодействует с внешними системами, которые не используют smear, возможна 1-секундная несогласованность в момент событие.

### Совет 5: Для финансовых систем

Финансовые системы, требующие точных временны́х меток (MiFID II, etc.), должны использовать TAI или PTP. TAI не имеет прерываний и является предпочтительным стандартом для торговых систем.

```python
# Пример: работа с TAI в Python (требует ручного учёта)
LEAP_SECONDS_TABLE = {
    # tai_timestamp: utc_offset
    1483228800 + 37: 37,  # 2017+
    # ... таблица всех коррекций
}

def utc_to_tai(utc_timestamp):
    """Конвертация UTC в TAI (простое приближение)"""
    # В реальности нужна полная таблица высокосных секунд
    return utc_timestamp + 37
```

## Итог

Высокосные секунды — элегантный компромисс между физическим вращением Земли и удобством атомного времени, который превратился в технологический кошмар эпохи интернета.

Ключевые факты:
1. **Причина**: Земля замедляется, разница UTC и астрономического времени не должна превышать 0.9 с
2. **IERS** объявляет о добавлении за 6 месяцев; секунды добавляются в конце июня или декабря
3. **Unix time** обходит проблему, игнорируя секунду 60 (двойная 23:59:59)
4. **Реальные баги**: Linux 2012, Cloudflare 2017, многочисленные Java-приложения
5. **Google Smear**: растянуть добавление на 24 часа, избегая прыжка
6. **WRC-23 2023**: решено отложить проблему до ~2135 года
