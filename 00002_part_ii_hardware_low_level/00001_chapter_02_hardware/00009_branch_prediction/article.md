# Предсказатель переходов (branch prediction)

## Введение

В 2012 году один вопрос на Stack Overflow потряс сообщество разработчиков: «Почему обработка отсортированного массива быстрее, чем неотсортированного?» Автор обнаружил, что простой цикл с условием работает почти в 6 раз быстрее, если данные предварительно отсортированы — хотя сама сортировка не меняла количество сравнений. Ответ оказался в предсказателе переходов процессора.

Предсказатель переходов — это аппаратная подсистема, которая угадывает результат условного перехода до того, как он был вычислен. Если предсказание верно, конвейер работает без пауз. Если нет — все инструкции, загруженные «не в ту ветку», нужно выбросить, а конвейер перезагрузить. В современных процессорах с глубокими конвейерами (14-19 стадий) это стоит 15-20 тактов — и именно это определяет эффективность многих алгоритмов.

Эта тема находится на стыке архитектуры процессора, безопасности (атака Spectre основана на предсказателе) и написания высокопроизводительного кода. Понимание предсказателя переходов — обязательный навык для системного программиста и архитектора высоконагруженных систем.

## 1. Зачем нужно предсказание

### 1.1 Проблема управляющих опасностей

Вспомним: в конвейере процессор выбирает (fetch) инструкции последовательно, опережая выполнение. Когда конвейер встречает условный переход:

```assembly
; x86-64: условный переход
cmp    rax, rbx
jge    .label_true    ; если rax >= rbx — прыгаем
; ... код если false ...
.label_true:
; ... код если true ...
```

Условие `rax >= rbx` вычисляется в стадии Execute (EX). К этому моменту конвейер уже загрузил 3-5 следующих инструкций. Какие? Неизвестно до вычисления.

Без предсказания — три варианта:
1. **Flush и ждать** — вставлять пузыри до вычисления условия. Потеря 3-5 тактов на каждый переход.
2. **Выполнять обе ветви** — дорого по ресурсам, не масштабируется.
3. **Предсказывать** — угадывать, какая ветвь будет взята, и загружать её инструкции. При правильном предсказании — ноль потерь.

Вариант 3 — выбор всех современных процессоров.

### 1.2 Цена ошибки предсказания

Цена misprediction зависит от глубины конвейера до точки вычисления условия:

| Процессор | Длина конвейера | Штраф misprediction |
|-----------|-----------------|---------------------|
| ARM Cortex-A7 | 8 стадий | 7-10 тактов |
| Intel Core 2 | 14 стадий | 12-14 тактов |
| Intel Skylake | 14-19 стадий | 14-19 тактов |
| AMD Zen 4 | 19 стадий | 15-20 тактов |
| Intel Pentium 4 (Prescott) | 31 стадия | 20-31 такт |

Если программа выполняет 1 миллиард переходов в секунду и 10% из них предсказаны неверно, то при штрафе 15 тактов:

Потери $= 1 \cdot 10^9 \times 0.1 \times 15$ тактов $= 1.5 \cdot 10^9$ тактов $= 0.5$ секунды при 3 ГГц.

## 2. Статическое предсказание

Самый простой вид предсказания — статический, не зависящий от истории выполнения.

### 2.1 Стратегии статического предсказания

**Predict not-taken:** всегда предполагать, что переход не будет взят — загружать следующую по порядку инструкцию. Работает хорошо для `if`-блоков (тело `if` часто выполняется), плохо для циклов (обратный переход в начало выполняется почти всегда).

**Predict taken:** всегда предполагать, что переход взят. Лучше для обратных переходов (циклы), хуже для прямых.

**BTFN (Backward Taken, Forward Not-Taken):** гибрид — обратные переходы (на меньший адрес) считаются взятыми (циклы), прямые — нет (редкие ветки). Это правило использовалось в ранних SPARC и MIPS.

Точность статических методов: около 65-70% — лучше чем случайное угадывание (50%), но далеко от современных 95-99%.

### 2.2 Аннотации компилятора

Компилятор может сообщить процессору ожидаемое направление перехода:

```c
// GCC/Clang: __builtin_expect(expr, expected)
if (__builtin_expect(error_condition, 0)) {
    // редкий путь — likely false
    handle_error();
}

// C++20: [[likely]] / [[unlikely]]
if (x > 0) [[likely]] {
    // часто выполняемый путь
    process(x);
} else [[unlikely]] {
    handle_negative();
}
```

В Linux kernel повсюду используются макросы `likely()` и `unlikely()`:

```c
// include/linux/compiler.h
#define likely(x)    __builtin_expect(!!(x), 1)
#define unlikely(x)  __builtin_expect(!!(x), 0)

// Пример использования:
if (unlikely(signal_pending(current)))
    return -ERESTARTSYS;
```

Эти аннотации влияют не только на предсказание, но и на порядок кода — компилятор помещает «горячий» путь первым, улучшая кеш инструкций.

## 3. Динамическое предсказание

Динамическое предсказание использует историю выполнения конкретных переходов для прогноза их поведения в будущем.

### 3.1 1-bit предсказатель

Простейший: для каждого перехода (идентифицируемого адресом) хранится 1 бит — «был ли переход взят в последний раз».

Проблема: для цикла вида `for (i = 0; i < 100; i++)` переход в конец выполнен 99 раз и не выполнен 1 раз (выход). 1-битный предсказатель даёт 2 ошибки на цикл:
- Первая итерация (ещё не знает, что будет взят)
- Последняя итерация (ожидал «взят», а переход не выполнился)

В пристальном вложенном цикле — ошибки на каждой итерации внешнего цикла.

### 3.2 2-bit saturating counter

Решение: 2-битный насыщающий счётчик с состояниями:
- `00` — Strongly Not Taken (SNT)
- `01` — Weakly Not Taken (WNT)
- `10` — Weakly Taken (WT)
- `11` — Strongly Taken (ST)

Переход: если текущее состояние $\geq$ `10` → предсказываем «взят», иначе «не взят».

При каждом взятом переходе счётчик инкрементируется (с насыщением на `11`). При невзятом — декрементируется (с насыщением на `00`).

```
Цикл на 100 итерациях:
- Начальное состояние: SNT (00)
- Итерация 1 (взят): 00 → 01 (ошибка предсказания, был SNT)
- Итерация 2 (взят): 01 → 10 (ошибка предсказания, был WNT)
- Итерации 3-99 (взят): остаётся в ST (11) — все правильно
- Итерация 100 (не взят): 11 → 10 (ошибка предсказания — неверно предсказали ST)
- После цикла: 10 (WT) — при следующей итерации внешнего цикла снова одна ошибка
```

Итого: 3 ошибки вместо 2 у однобитного? Нет — для вложенных циклов 2-bit лучше: он «помнит» состояние через одно исключение (выход из цикла), тогда как 1-bit немедленно меняет предсказание.

### 3.3 Branch History Table (BHT / PHT)

Таблица предсказателей — массив 2-битных счётчиков, индексируемый по младшим битам адреса перехода (PC):

```
Branch Address:  0x10040A1C
Нижние 12 бит:   0b 1010 0001 1100 = 0xA1C = 2588

BHT[2588] → 2-bit counter (например, ST=11)
Предсказание: Taken
```

Размер BHT: обычно 1K-64K записей. Проблема: aliasing — разные переходы маппируются на одну запись, интерферируют.

### 3.4 Global History Register (GHR) и Correlated Prediction

Предсказание можно улучшить, учитывая не только историю данного перехода, но и историю последних N переходов в программе.

**GHR (Global History Register):** сдвиговый регистр, хранящий результаты последних N переходов (1 = взят, 0 = не взят). Обычно 8-16 бит.

**Индексация по XOR(PC, GHR):** объединяем адрес перехода с глобальной историей, получая более точный индекс:

```
GHR:    1101 0101 (последние 8 переходов)
PC:     0xA1C (младшие 8 бит: 0001 1100)
XOR:    1100 1001 → индекс в PHT (Pattern History Table)
```

Эта техника называется **Two-Level Adaptive Prediction** (Yeh & Patt, 1991). Позволяет предсказывать паттерны типа «взят-не взят-взят-взят» с высокой точностью.

### 3.5 Tournament Predictor (гибрид)

Процессор не знает заранее, какой предсказатель лучше для данного перехода. Решение — содержать несколько предсказателей и выбирать между ними:

- **Local predictor:** история данного конкретного перехода
- **Global predictor:** глобальная история переходов
- **Choice predictor (Meta-predictor):** хранит историю того, какой из двух предсказателей оказывался прав

Такой предсказатель использовался в Alpha 21264 (1998) и дал точность ~97%.

## 4. BTB — Branch Target Buffer

Предсказатель переходов решает вопрос «будет ли переход взят?». Но для косвенных переходов (indirect branches) и прямых переходов нужно ещё знать **куда** прыгнуть:

```assembly
jmp [rax]           ; косвенный переход — адрес в регистре
call [rdi + 0x18]   ; виртуальная функция — адрес в vtable
ret                  ; возврат — адрес в стеке
```

**Branch Target Buffer (BTB)** — кеш-таблица последних N переходов, хранящая пары (адрес перехода → целевой адрес). Ещё до декодирования инструкции, на стадии Fetch, CPU проверяет BTB по текущему PC:

- Если PC есть в BTB → немедленно начинаем fetch по целевому адресу
- Если нет → fetch по PC+4 (консервативно: считаем, что перехода нет)

Размер BTB: 256-4096 записей. Eviction при переполнении — LRU или случайный.

### 4.1 Return Stack Buffer (RSB)

Специальный предсказатель для инструкций `ret` — маленький стек (8-32 записи), который зеркалирует аппаратный call stack:

- При `call addr` → pushаем (call_PC + инструкция_длина) в RSB
- При `ret` → popаем из RSB и используем как целевой адрес

RSB работает идеально для обычных функций. Проблемы возникают при:
- Очень глубокой рекурсии (RSB переполняется)
- Хвостовых вызовах
- Longjmp, coroutines

## 5. Знаменитый пример: отсортированный массив

Это тот самый вопрос со Stack Overflow (2012), набравший 30 000+ голосов.

### 5.1 Исходный код

```cpp
#include <algorithm>
#include <ctime>
#include <iostream>

int main() {
    const int N = 32768;
    int data[N];
    for (int i = 0; i < N; ++i)
        data[i] = rand() % 256;

    // Тест 1: неотсортированный
    long long sum = 0;
    for (int i = 0; i < 100000; ++i)
        for (int j = 0; j < N; ++j)
            if (data[j] >= 128)  // ← этот переход
                sum += data[j];

    // Тест 2: отсортированный
    std::sort(data, data + N);
    sum = 0;
    for (int i = 0; i < 100000; ++i)
        for (int j = 0; j < N; ++j)
            if (data[j] >= 128)  // ← тот же переход
                sum += data[j];
}
```

Результат на Core i7:
- Неотсортированный: ~11.54 секунды
- Отсортированный: ~1.93 секунды
- Ускорение: **$5.98\times$**

### 5.2 Почему отсортированный быстрее

**Неотсортированный массив:** значения случайны — переход `data[j] >= 128` случайно взят или нет. Предсказатель угадывает ~50% — половина итераций сбрасывает конвейер.

**Отсортированный массив:** первая половина массива (значения 0-127) — переход всегда НЕ взят. Вторая половина (128-255) — всегда взят. Предсказатель быстро обучается и угадывает почти всегда верно (кроме одной ошибки в точке перехода 127→128).

Число операций одинаково в обоих случаях! Разница только в поведении предсказателя.

### 5.3 Branchless-вариант (максимальная скорость)

```cpp
// Избегаем ветвления полностью:
long long sum = 0;
for (int j = 0; j < N; ++j) {
    int t = (data[j] - 128) >> 31;  // -1 если data[j] < 128, 0 иначе
    sum += ~t & data[j];              // добавляем только если >= 128
}
```

Эта версия работает одинаково быстро для отсортированного и неотсортированного массива, и примерно равна скорости «отсортированной» версии — без какой-либо сортировки.

Компилятор с `-O2` обычно сам генерирует `CMOV` (conditional move):

```assembly
; clang -O2:
.loop:
    mov    eax, dword ptr [rdi]
    cmp    eax, 127
    jle    .skip                  ; или CMOV-вариант:
    add    qword ptr [rsp], rax
.skip:
    add    rdi, 4
    dec    rcx
    jnz    .loop

; С auto-branchless (-O3 или __builtin_expect):
    movsx  rax, dword ptr [rdi]
    cmp    eax, 127
    cmovle rax, rcx              ; rcx = 0
    add    rdx, rax              ; добавляем 0 или data[j]
```

## 6. Spectre — когда предсказание стало уязвимостью

В январе 2018 года исследователи Project Zero (Google) опубликовали описание атаки Spectre, которая использует именно механизм спекулятивного выполнения и предсказания переходов.

### 6.1 Spectre Variant 1: Bounds Check Bypass

```c
// Код жертвы (в ядре ОС или другом процессе):
uint8_t array1[16];
uint8_t array2[256 * 4096];

void vulnerable_function(size_t x) {
    if (x < array1_size) {           // (A) — проверка границ
        uint8_t y = array1[x];       // (B) — чтение элемента
        temp = array2[y * 4096];     // (C) — зависимый доступ
    }
}
```

**Атака:**
1. Атакующий вызывает `vulnerable_function` много раз с корректными `x` → предсказатель обучается: «переход (A) всегда взят».
2. Атакующий вызывает с `x` = адрес секретных данных (за пределами array1).
3. Предсказатель предсказывает: «переход (A) взят» → **спекулятивно** выполняет строки B и C.
4. Затем (A) вычисляется, обнаруживается нарушение → результаты откатываются.
5. Но строка (C) оставила след в **кеше** — array2[secret * 4096] закешировался!
6. Атакующий измеряет время доступа ко всем 256 элементам array2 → элемент с наименьшей задержкой раскрывает значение secret.

Это **атака через побочный канал кеша** (cache timing side channel), ставшая возможной благодаря спекулятивному выполнению.

### 6.2 Патчи против Spectre

- **LFENCE (x86):** барьер инструкции — останавливает спекуляцию до выполнения.
- **Retpoline:** замена косвенного перехода на конструкцию, которая «ловит» спекуляцию в бесконечный цикл:

```assembly
; Retpoline для: jmp [rax]
call set_up_target
.loop:
    pause       ; говорим CPU: это spin-wait
    lfence
    jmp .loop
set_up_target:
    mov [rsp], rax   ; подменяем адрес возврата
    ret              ; RSB предсказывает .loop, но ret попадает на rax
```

- **Masking:** проверка `x < size` заменяется на `x &= mask` где mask гарантирует безопасный диапазон.

### 6.3 Производительность и безопасность

Патчи Spectre замедлили некоторые приложения на 5-30%. Syscall-интенсивные программы (базы данных, веб-серверы) пострадали сильнее всего. Это наглядно демонстрирует, что микроархитектурные оптимизации могут иметь значительные последствия для безопасности.

## 7. Современные предсказатели: TAGE

Современные процессоры (Intel Haswell+, AMD Zen, Apple M1+) используют семейство предсказателей **TAGE (TAgged GEometric history length predictor)**.

### 7.1 Принцип TAGE

TAGE состоит из базового предсказателя и нескольких таблиц с различными длинами истории:

```
Базовый предсказатель (T0):
  - Индексируется по PC
  - Хранит 2-bit counter

Таблица T1 (история 4 бита):
  - Индексируется по hash(PC, GHR[0:3])
  - Хранит: тег (partial PC), 3-bit counter, 1-bit usefulness

Таблица T2 (история 8 бит):
  - Индексируется по hash(PC, GHR[0:7])

Таблица T3 (история 16 бит):
  - Индексируется по hash(PC, GHR[0:15])

Таблица T4 (история 32 бита):
  - ...
```

Длины истории растут геометрически: 4, 8, 16, 32, ... — отсюда название «Geometric».

Предсказание: используется таблица с наибольшей историей, у которой тег совпадает с текущим PC. Если нет совпадений — базовый предсказатель.

### 7.2 Точность TAGE

На стандартных тестах CBP (Championship Branch Prediction):

| Предсказатель | Mispredictions на 1000 инструкций (MPKI) |
|---------------|------------------------------------------|
| Static (not-taken) | ~50 |
| 2-bit Bimodal | ~15 |
| gshare (Global) | ~8 |
| Tournament (Alpha 21264) | ~5 |
| TAGE | ~2-3 |
| TAGE + Neural | ~1-1.5 |

TAGE снизил ошибки предсказания в 2-3 раза по сравнению с tournament predictor 1990-х.

### 7.3 Neural Branch Prediction

Последние процессоры AMD (Zen 2+) и, предположительно, Apple M-серий используют нейросетевые предсказатели — персептрон, обученный на истории переходов:

```
Вход:  GHR[0], GHR[1], ..., GHR[n]  (биты истории переходов)
Веса:  w0, w1, ..., wn  (обучаемые)
Сумма: Σ wi * GHR[i]
Предсказание: Taken если сумма > 0
Обновление: wi += (1 if taken else -1) * GHR[i]
```

Персептрон хорошо улавливает сложные паттерны с длинной историей, где TAGE затруднён.

## 8. Практические рекомендации

### 8.1 Когда предсказатель «ломается»

1. **Данные-зависимые ветвления с хаотичными данными:** обработка пакетов, парсинг, криптография.

2. **Виртуальные функции в критических петлях:** каждый виртуальный вызов — косвенный переход, BTB должен знать все возможные цели.

3. **Переключатели (switch) по большому числу вариантов:** компилируется в jump table (косвенный переход).

### 8.2 Техники оптимизации

**Деполиморфизм (devirtualization):** компилятор угадывает наиболее вероятный тип и делает direct call с проверкой:

```cpp
// Оригинал:
virtual void process(Data* d);

// После PGO (Profile-Guided Optimization):
if (__builtin_expect(dynamic_cast<ConcreteType*>(obj) != nullptr, 1)) {
    static_cast<ConcreteType*>(obj)->ConcreteType::process(d);  // direct call
} else {
    obj->process(d);  // fallback virtual
}
```

**Сортировка данных перед обработкой:** если алгоритм позволяет — отсортировать входные данные по критерию ветвления:

```python
# Медленно (случайные ветвления):
for item in items:
    if item.type == 'A':
        process_a(item)
    else:
        process_b(item)

# Быстрее (предсказатель обучается на длинных сериях):
items_a = [x for x in items if x.type == 'A']
items_b = [x for x in items if x.type == 'B']
for item in items_a:
    process_a(item)
for item in items_b:
    process_b(item)
```

**Branchless programming:** замена if-else на арифметические операции:

```c
// Ветвление:
int clamp(int x, int lo, int hi) {
    if (x < lo) return lo;
    if (x > hi) return hi;
    return x;
}

// Branchless:
int clamp_branchless(int x, int lo, int hi) {
    x = x < lo ? lo : x;   // компилятор → CMOV
    x = x > hi ? hi : x;
    return x;
}

// Или явно:
int clamp_explicit(int x, int lo, int hi) {
    return x ^ ((x ^ lo) & -(x < lo)) ^ ((x ^ hi) & -(x > hi));
}
```

| Год | Процессор | Предсказатель | Точность |
|-----|-----------|---------------|----------|

## Заключение

Предсказатель переходов — один из наиболее изощрённых элементов современного процессора. Он превратился из простого 1-битного переключателя в сложную систему с многоуровневыми таблицами истории, нейросетевыми компонентами и специализированными предсказателями для циклов, возвратов и косвенных переходов.

Для программиста ключевые выводы:

1. **Предсказуемые ветвления дёшевы** — если ветвь всегда берётся или никогда, предсказатель легко обучается.

2. **Хаотичные ветвления дороги** — случайные данные, хеш-таблицы, парсинг вынуждают конвейер постоянно сбрасываться.

3. **Branchless-код часто быстрее** — `CMOV` и битовая арифметика устраняют зависимость от предсказателя.

4. **Profile-Guided Optimization (PGO)** — компилятор с данными профилирования лучше расставляет аннотации `likely/unlikely`, выбирает layout кода.

5. **Spectre напомнил:** аппаратные оптимизации могут создавать уязвимости безопасности. Программисты, работающие с чувствительными данными, должны учитывать спекулятивное выполнение.
