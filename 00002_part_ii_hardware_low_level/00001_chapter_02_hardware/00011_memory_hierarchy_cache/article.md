# Иерархия памяти и кеши L1/L2/L3

## Введение

Есть одна ирония в истории вычислительной техники: процессоры становятся быстрее гораздо быстрее, чем память. С 1980 по 2000 год тактовая частота процессоров росла примерно на 55% в год, а скорость оперативной памяти — лишь на 7% в год. Сегодня разрыв между скоростью вычислений и скоростью доступа к памяти — один из главных факторов, ограничивающих производительность.

Решение этой проблемы — иерархия памяти: небольшой объём очень быстрой памяти рядом с процессором, более медленная и объёмная дальше. Кеш процессора — центральный элемент этой иерархии. Знаменитое утверждение Эдсгера Дейкстры «programming is not about typing, it's about thinking» можно перефразировать для производительности: «оптимизация — это не о вычислениях, это о памяти».

Понимание иерархии памяти и кешей — ключевой навык для написания быстрого кода. Разница между cache-friendly и cache-unfriendly алгоритмом может составлять 10-100× по производительности, даже если оба имеют одинаковую алгоритмическую сложность O(n).

## 1. Иерархия памяти

### 1.1 Уровни иерархии

Современная компьютерная система использует несколько уровней памяти, различающихся по скорости, объёму и стоимости:

| Уровень | Объём | Задержка | Пропускная способность |
|---------|-------|---------|----------------------|
| Регистры | 256-1024 байт | 0 тактов | Неограничена (внутри CPU) |
| L1 кеш | 32-64 КБ | 4-5 тактов (~1.5 нс) | 100-200 ГБ/с |
| L2 кеш | 256 КБ - 1 МБ | 12-15 тактов (~5 нс) | 50-100 ГБ/с |
| L3 кеш | 8-64 МБ | 30-50 тактов (~12-20 нс) | 30-60 ГБ/с |
| RAM (DRAM) | 8-128 ГБ | 200-300 тактов (~70-100 нс) | 30-60 ГБ/с |
| NVMe SSD | 1-8 ТБ | 50-100 мкс | 5-7 ГБ/с |
| SATA SSD | 1-8 ТБ | 100-200 мкс | 500 МБ/с |
| HDD | 1-20 ТБ | 5-10 мс | 100-200 МБ/с |
| Сеть (LAN) | — | 100-500 мкс | 1-100 Гбит/с |

Задержка L1 кеша (~4 такта) против задержки RAM (~300 тактов) — разница в 75×. За время одного обращения к RAM процессор мог бы выполнить 300 операций с данными из кеша.

### 1.2 Принцип локальности

Иерархия памяти работает, потому что программы демонстрируют **принцип локальности**:

- **Временная локальность (temporal locality):** если адрес памяти был использован сейчас, вероятно, он будет использован снова в ближайшее время (переменные в циклах, функции, счётчики).

- **Пространственная локальность (spatial locality):** если адрес A был использован, вероятно, будут использованы адреса, близкие к A (массивы, записи структур, последовательный код).

Кеш эксплуатирует оба вида локальности: хранит недавно использованные данные (temporal) и загружает сразу целую линейку кеша (spatial).

### 1.3 Числа, которые нужно знать


## 2. Устройство кеша процессора

### 2.1 Cache Line (Строка кеша)

Основная единица кеширования — **cache line** (строка кеша). На всех современных x86/ARM процессорах размер строки кеша равен **64 байта**.

Когда процессор обращается к байту в памяти (например, адрес 0x1004), он загружает не один байт, а целую строку — 64 байта, выровненных на кратный адрес (в данном случае 0x1000-0x103F). Это реализует пространственную локальность: соседние данные загружаются «бесплатно».

```c
// Эффект cache line:
int array[64];  // 64 * 4 байта = 256 байт = 4 строки кеша

array[0];  // Miss: загружается строка 0x0000-0x003F (array[0]-array[15])
array[1];  // Hit: уже в кеше!
array[16]; // Miss: загружается строка 0x0040-0x007F
array[31]; // Hit
array[32]; // Miss: новая строка
```

Размер кеш-строки объясняет, почему обход массива по строкам (row-major) быстрее, чем по столбцам (column-major).

### 2.2 Set-Associative Cache (Множественно-ассоциативный кеш)

Как процессор ищет данные в кеше? Нельзя просто «хешировать» адрес — нужен компромисс между скоростью поиска и гибкостью размещения.

Три варианта организации:

**Direct-mapped (прямое отображение):**
Каждый адрес памяти маппируется ровно в одну ячейку кеша. Самый быстрый поиск, но высокая вероятность конфликтов:

```
Адрес:  [tag | index | offset]
         tag   →  проверяем совпадение с хранимым tag
         index →  номер строки в кеше
         offset → байт внутри строки
```

**Fully associative (полностью ассоциативный):**
Любой адрес может храниться в любой строке кеша. Нет конфликтов, но поиск требует параллельного сравнения со всеми строками — дорого для больших кешей.

**N-way set associative (N-путевой):**
Компромисс: кеш разбит на «сеты», каждый сет содержит N строк («путей»). Адрес маппируется в конкретный сет, но может занять любую из N строк этого сета.

```
4-way set associative L1 кеш (32 KB):
- Размер строки:    64 байта
- Число строк:      32768 / 64 = 512
- Число сетов:      512 / 4 = 128
- Разбиение адреса: [tag(52 бита) | set index(7 бит) | offset(6 бит)]
```

Типичные конфигурации:
| Уровень | Ассоциативность | Число сетов (типично) |
|---------|-----------------|----------------------|
| L1 | 4-way или 8-way | 64-128 |
| L2 | 8-way | 256-512 |
| L3 | 12-16-way | тысячи |
| TLB | 4-8-way | 64-128 |

### 2.3 Политика замещения: LRU

При промахе (cache miss) и заполненном сете какую строку вытеснить?

**LRU (Least Recently Used):** вытесняем строку, к которой дольше всего не обращались. Хорошо соответствует принципу временной локальности.

**Pseudo-LRU:** точный LRU для N-way требует N-1 бит на сет. Большинство процессоров используют приближение — дерево битов (PLRU, TPLRU).

**Random replacement:** случайный выбор. Проще в реализации, приемлемое качество.

**RRIP (Re-Reference Interval Prediction):** Intel использует вариант RRIP в L3, который лучше справляется со scan-операциями (последовательным обходом больших массивов, который иначе «вымывает» весь кеш).

### 2.4 Типы промахов

Три «C» в классификации промахов кеша:

- **Compulsory miss (обязательный):** первое обращение к данным — их ещё нет в кеше. Неизбежны, можно снизить prefetching.

- **Capacity miss (ёмкостный):** данных больше, чем кеш может вместить. Уменьшить рабочий набор или перейти на уровень кеша выше.

- **Conflict miss (конфликтный):** в direct-mapped или ограниченно-ассоциативном кеше разные данные борются за одни строки. Решение: padding, изменение stride доступа.

## 3. Многоуровневые кеши

### 3.1 L1, L2, L3 на современных процессорах

**L1 кеш** — самый быстрый, расположен непосредственно внутри ядра CPU. Обычно раздельный: L1i (инструкции) и L1d (данные). Размер: 32-64 КБ каждый. Задержка: 4-5 тактов. Полностью включён (inclusive) или эксклюзивный (exclusive) по отношению к L2.

**L2 кеш** — второй уровень, единый (unified), больше и медленнее. Обычно принадлежит отдельному ядру (per-core). Размер: 256 КБ - 1 МБ. Задержка: 12-15 тактов.

**L3 кеш (Last-Level Cache, LLC)** — разделяется между всеми ядрами процессора. Размер: 8-64 МБ (у AMD Ryzen до 128 МБ с 3D V-Cache). Задержка: 30-50 тактов. Критически важен для многопоточных программ.

Intel Skylake (6 ядер, 12-е поколение):
```
Core 0:   L1i(32KB) + L1d(32KB) + L2(256KB)
Core 1:   L1i(32KB) + L1d(32KB) + L2(256KB)
...
Core 5:   L1i(32KB) + L1d(32KB) + L2(256KB)
         ────────────────────────────────────
         Shared L3 (12 MB) — доступен всем ядрам
         ────────────────────────────────────
         Main Memory (DRAM)
```

### 3.2 Инклюзивные vs Эксклюзивные кеши

**Inclusive:** каждый уровень содержит полное подмножество следующего. L3 содержит всё, что есть в L1 и L2. Упрощает когерентность кеша: при инвалидации строки в L3 достаточно инвалидировать её везде. Недостаток: меньше эффективная ёмкость (L3 «тратит» место на дублирование L1/L2).

**Exclusive:** данных не дублируются между уровнями. L1 miss → строка идёт в L2, вытесняя одну строку из L2 в L3 (victim cache). Более эффективное использование памяти кеша. AMD использует эксклюзивную политику.

**Non-inclusive non-exclusive (NINE):** последние Intel (начиная с Ice Lake) используют гибридную политику для L3.

## 4. Cache-Friendly код

### 4.1 Row-major vs Column-major доступ

Классический пример влияния кеша — умножение матриц или простой проход:

```c
#define N 1024

double A[N][N];  // строки хранятся последовательно в памяти

// Вариант 1: обход по строкам (row-major) — cache-friendly
void row_major_sum() {
    double sum = 0;
    for (int i = 0; i < N; i++)
        for (int j = 0; j < N; j++)
            sum += A[i][j];  // A[i][j] и A[i][j+1] — соседи в памяти
}

// Вариант 2: обход по столбцам — cache-unfriendly
void col_major_sum() {
    double sum = 0;
    for (int j = 0; j < N; j++)
        for (int i = 0; i < N; i++)
            sum += A[i][j];  // A[i][j] и A[i+1][j] — 1024*8 = 8192 байт друг от друга
}
```

При N=1024, double (8 байт):
- Шаг строки: 8 байт (одна cache line обслуживает 8 элементов)
- Шаг столбца: 8192 байт (каждый элемент — новая cache line!)

Типичные результаты:
- Row-major: ~0.5 с
- Column-major: ~3-4 с (6-8× медленнее!)

### 4.2 Matrix Multiplication с Blocking (Tiling)

Стандартный алгоритм умножения матриц имеет плохую кеш-локальность при больших матрицах:

```c
// Наивный O(n³):
void matmul_naive(double A[N][N], double B[N][N], double C[N][N]) {
    for (int i = 0; i < N; i++)
        for (int j = 0; j < N; j++)
            for (int k = 0; k < N; k++)
                C[i][j] += A[i][k] * B[k][j];
    // Внутренний цикл: B[k][j] — шаг N*8 байт, каждый — cache miss!
}
```

**Cache-blocking (тайлинг):**

```c
// Разбиваем на блоки BLOCK×BLOCK, умещающиеся в L1/L2:
#define BLOCK 64  // 64*64*8 байт = 32 KB ≈ размер L1

void matmul_blocked(double A[N][N], double B[N][N], double C[N][N]) {
    for (int ii = 0; ii < N; ii += BLOCK)
      for (int jj = 0; jj < N; jj += BLOCK)
        for (int kk = 0; kk < N; kk += BLOCK)
          // Внутренний блок — всё умещается в L1:
          for (int i = ii; i < ii + BLOCK; i++)
            for (int j = jj; j < jj + BLOCK; j++)
              for (int k = kk; k < kk + BLOCK; k++)
                C[i][j] += A[i][k] * B[k][j];
}
```

Почему это помогает: блок размером BLOCK×BLOCK умещается в L1 кеш. Внутри блока элемент матрицы A[i][k] используется BLOCK раз подряд — он остаётся в L1. Аналогично для B[k][j]. Число cache miss уменьшается в BLOCK раз.

Для N=1024, BLOCK=64:
- Наивный: ~12 секунд
- Blocked: ~1.5 секунды (8× ускорение!)

### 4.3 Padding для устранения конфликтных промахов

Иногда две структуры данных маппируются на один и тот же сет кеша и вытесняют друг друга. Это особенно часто при степенях двойки:

```c
// Проблема: матрицы 1024×1024 — stride 4096 байт = 64 строки кеша
// При 8-way ассоциативности: через 8*64 = 512 строк — конфликт!

// Решение: добавить padding, чтобы сдвинуть страйд:
double A[1024][1024 + 8];  // +8 double = +64 байта padding
double B[1024][1024 + 8];
// Теперь A[i] и B[i] не конкурируют за одни строки кеша
```

### 4.4 Структуры данных и кеш

```c
// Плохо: структура с холодными полями рядом с горячими
struct Employee {
    char name[64];      // 64 байта — часто не нужны при фильтрации
    int   department;   // горячее поле
    double salary;      // горячее поле
    char  address[256]; // 256 байт — почти никогда не нужны
    int   age;          // горячее поле
};

// При обходе массива employees для фильтрации по department/salary/age:
// Каждый элемент = 64+4+8+256+4 = 336 байт → 6 строк кеша
// Но нам нужны только 16 байт (department + salary + age)

// Хорошо: разделить горячие и холодные данные
struct EmployeeHot {
    int    department;
    double salary;
    int    age;
};  // 16 байт → 4 элемента в одну строку кеша!

struct EmployeeCold {
    char name[64];
    char address[256];
};

EmployeeHot  employees_hot[N];   // для фильтрации
EmployeeCold employees_cold[N];  // только для отображения
```

## 5. Prefetching

### 5.1 Hardware Prefetcher

Современные процессоры имеют аппаратные prefetcher-ы (Stride Prefetcher, Stream Prefetcher), которые автоматически определяют паттерны доступа к памяти и загружают данные заранее:

- **Stream prefetcher:** обнаруживает последовательный доступ (a[0], a[1], a[2], ...) и загружает следующие строки кеша.
- **Stride prefetcher:** обнаруживает регулярный шаг (a[0], a[4], a[8], ...) и загружает строки с тем же шагом.

Hardware prefetcher отлично работает для простых паттернов. Не работает для случайного доступа (linked lists, хеш-таблицы, деревья).

### 5.2 Software Prefetching

Программист может явно указать CPU загрузить данные заранее:

```c
#include <xmmintrin.h>

void process_with_prefetch(int *data, int n) {
    const int PREFETCH_DIST = 16;  // загружать 16 элементов вперёд
    
    for (int i = 0; i < n; i++) {
        if (i + PREFETCH_DIST < n) {
            _mm_prefetch((char*)&data[i + PREFETCH_DIST], _MM_HINT_T0);
            // T0 = L1, T1 = L2, T2 = L3, NTA = non-temporal (не кешировать)
        }
        process(data[i]);
    }
}
```

Для linked list — software prefetch особенно важен, так как hardware prefetcher не может предсказать следующий указатель:

```c
struct Node {
    int value;
    Node *next;
};

void traverse_with_prefetch(Node *head) {
    Node *curr = head;
    while (curr != nullptr) {
        if (curr->next)
            __builtin_prefetch(curr->next->next, 0, 1);  // prefetch через 2 узла
        process(curr->value);
        curr = curr->next;
    }
}
```

## 6. Кеш и многопоточность

### 6.1 False Sharing

Если два потока на разных ядрах изменяют **разные переменные, лежащие в одной кеш-строке**, возникает «ложное разделение» (false sharing):

```c
// Плохо: два счётчика в одной кеш-строке
struct SharedCounters {
    volatile int counter_a;  // поток 0 пишет
    volatile int counter_b;  // поток 1 пишет
};
// counter_a и counter_b — в одной кеш-строке (8 байт < 64 байта)!
// При записи одного — инвалидируется строка, другой поток получает miss
```

Решение и детали — в следующей статье про MESI. Здесь лишь упомянем: разделить на разные кеш-строки с padding.

### 6.2 NUMA (Non-Uniform Memory Access)

В многопроцессорных системах каждый процессор имеет «свою» DRAM — локальную и быструю. Доступ к памяти другого процессора («удалённой») — через межпроцессорную шину, медленнее:

```
NUMA Node 0:        NUMA Node 1:
  CPU 0-7             CPU 8-15
  L1/L2/L3            L1/L2/L3
  Local DRAM ←───→ Remote DRAM
  (fast: 100 ns)      (slow: 150-200 ns)
```

Оптимизация: размещать данные потока в «его» NUMA-узле:

```c
#include <numaif.h>

// Разместить память на конкретном NUMA-узле:
void *ptr = numa_alloc_onnode(size, node_id);

// Или использовать mbind:
mbind(ptr, size, MPOL_BIND, nodemask, maxnode, MPOL_MF_MOVE);
```

## 7. Инструменты анализа кеш-поведения

### 7.1 Valgrind/Cachegrind

```bash
# Симуляция кеша с Cachegrind:
valgrind --tool=cachegrind ./your_program

# Просмотр результатов:
cg_annotate cachegrind.out.12345

# Вывод:
# I1 miss rate:    0.00%
# LLi miss rate:   0.00%
# D1 miss rate:    2.13%   ← промахи L1 data cache

```

### 7.2 Linux perf

```bash
# Счётчики кеша через perf:
perf stat -e L1-dcache-loads,L1-dcache-load-misses,\
              LLC-loads,LLC-load-misses ./program

# Пример вывода:
# 1,000,000,000   L1-dcache-loads
#     50,000,000  L1-dcache-load-misses     # 5% miss rate — приемлемо
#      2,000,000  LLC-loads
#        500,000  LLC-load-misses            # 25% — много, стоит оптимизировать
```

### 7.3 perf mem для анализа паттернов доступа

```bash
# Сэмплирование медленных обращений к памяти:

perf mem report

# Показывает горячие адреса с высокой латентностью — точки оптимизации
```

## 8. Практические паттерны

### 8.1 Locality-Aware алгоритмы

**Бинарный поиск vs B-tree:**
- Бинарный поиск в отсортированном массиве из 1M элементов: 20 сравнений, но каждое — потенциальный cache miss (случайный доступ).
- B-tree с широкими узлами (64 байта = 1 кеш-строка): меньше уровней, каждый узел — одно cache miss, зато обслуживает 8-16 ключей.

**Van Emde Boas layout (cache-oblivious layout):**
Рекурсивное размещение дерева: корень → левое поддерево → правое поддерево. Обеспечивает хорошую кеш-локальность на всех уровнях иерархии без явного знания размера кеша.

### 8.2 Компактное представление данных

```c
// Вместо float[4] для небольших значений — uint8[4]:
// float: 4 байта на элемент, 16 элементов в строке кеша
// uint8: 1 байт на элемент, 64 элемента в строке кеша!

// Квантование для ML inference (int8 вместо float32):
// 4× меньше памяти → 4× больше данных в кеше → 4× меньше промахов

// Bitset для флагов:
#include <bitset>
std::bitset<1000000> flags;  // 125 KB vs 1 MB для bool[1000000]
```

### 8.3 Loop Fusion и Loop Fission

**Loop fusion:** объединение двух циклов в один, чтобы использовать данные пока они в кеше:

```c
// До fusion: два прохода — данные загружаются дважды:
for (int i = 0; i < n; i++) b[i] = a[i] * 2;
for (int i = 0; i < n; i++) c[i] = b[i] + 1;

// После fusion: один проход — b[i] вычисляется и сразу используется:
for (int i = 0; i < n; i++) {
    b[i] = a[i] * 2;
    c[i] = b[i] + 1;  // b[i] ещё в регистре или L1
}
```

**Loop fission:** наоборот, разделение цикла для улучшения векторизации или устранения зависимостей.

## 9. Пример: профилирование и оптимизация

### 9.1 Медленная функция — поиск

```c
// Поиск элемента в несортированном массиве структур:
typedef struct {
    int key;
    char data[60];  // 60 байт «холодных» данных
} Record;           // 64 байта = ровно одна кеш-строка

Record records[100000];

int find_key(int target) {
    for (int i = 0; i < 100000; i++)
        if (records[i].key == target)  // но мы загружаем все 64 байта!
            return i;
    return -1;
}
```

### 9.2 Оптимизированная версия

```c
// Разделение: только ключи в отдельном массиве
int keys[100000];    // 400 KB — умещается в L2!
Record records[100000];

int find_key_opt(int target) {
    // Поиск только по keys[] — 16 ключей в кеш-строке:
    for (int i = 0; i < 100000; i++)
        if (keys[i] == target)
            return i;
    return -1;
}
// Нашли индекс → обращаемся к records[index] один раз
```

Результат: в 4-8 раз быстрее при частых промахах, потому что в кеш-строку помещается в 16 раз больше ключей.

### 9.3 ещё оптимизация через SIMD

```c
// Vectorized search — 8 ключей за такт (AVX2):
#include <immintrin.h>

int find_key_simd(int *keys, int n, int target) {
    __m256i vtarget = _mm256_set1_epi32(target);
    for (int i = 0; i < n - 7; i += 8) {
        __m256i vkeys = _mm256_loadu_si256((__m256i*)(keys + i));
        __m256i cmp = _mm256_cmpeq_epi32(vkeys, vtarget);
        int mask = _mm256_movemask_epi8(cmp);
        if (mask) return i + __builtin_ctz(mask) / 4;
    }
    // Обработка хвоста...
    return -1;
}
```

Комбинация разделения данных + SIMD: ускорение 20-40× по сравнению с исходной версией.

## Заключение

Иерархия памяти — это не детали реализации, это архитектурный принцип, который определяет производительность любой программы. Понимание кешей объясняет:

- Почему NumPy в 100× быстрее чистого Python (SIMD + кеш-локальность)
- Почему хорошая БД хранит индексы в B-деревьях (кеш-эффективные для дискового доступа)
- Почему матричные операции требуют блочного (tiled) алгоритма
- Почему AOS медленнее SOA для SIMD-кода
- Почему linked list проигрывает массиву при итерации

Правило большого пальца: если производительность кажется неожиданно низкой, первое что нужно проверить — не алгоритмическую сложность, а паттерны обращения к памяти. Инструменты (perf, valgrind/cachegrind, vtune) покажут точку проблемы. Затем — реструктурировать данные (SOA, разделение горячего/холодного, padding) и алгоритм (blocking, prefetching, SIMD).
