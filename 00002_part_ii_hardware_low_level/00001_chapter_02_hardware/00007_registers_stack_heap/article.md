# Регистры, стек и куча — где живут переменные

## Введение

Каждая переменная в программе должна где-то физически располагаться. На самом высоком уровне абстракции разработчик просто объявляет `int x = 42` и не задумывается о деталях. Но в реальности процессор и операционная система используют несколько принципиально разных механизмов хранения данных: регистры процессора, стек (stack) и кучу (heap). Понимание разницы между ними критически важно для написания производительного кода и понимания причин ошибок вроде stack overflow или use-after-free.

В этой статье мы разберём, где именно «живут» переменные: когда они хранятся в регистрах, когда попадают на стек, а когда выделяются в куче. Мы рассмотрим организацию стекового фрейма, механизм вызова функций, принципиальные различия стека и кучи и типичные ошибки, связанные с каждым из этих механизмов.

## 1. Регистры процессора

Самый быстрый вид хранения данных — регистры процессора. Доступ к регистру занимает ноль тактов дополнительной задержки (данные уже находятся внутри процессора), тогда как доступ к оперативной памяти занимает сотни тактов.

### Регистры общего назначения x86-64

В архитектуре x86-64 доступно 16 регистров общего назначения, каждый шириной 64 бита:

```
RAX, RBX, RCX, RDX  — «исторические» регистры
RSI, RDI             — индексные регистры (source/destination index)
RSP                  — Stack Pointer (указатель стека)
RBP                  — Base Pointer (базовый указатель фрейма)
R8–R15               — «новые» регистры, добавленные в x86-64
```

Регистр можно рассматривать как именованную переменную шириной 64 бита, существующую непосредственно в процессоре. Компилятор стремится хранить «горячие» переменные в регистрах, избегая обращений к памяти.

### Специальные регистры

**RSP (Stack Pointer)** — всегда указывает на верхушку стека (текущую вершину стека вызовов). В x86-64 стек растёт «вниз»: когда что-то кладётся на стек, RSP уменьшается.

**RBP (Base Pointer / Frame Pointer)** — указывает на начало текущего стекового фрейма. Используется для доступа к локальным переменным функции с фиксированными смещениями. При высоких уровнях оптимизации компилятор может не использовать RBP («omit frame pointer»), освобождая регистр для других нужд.

**RIP (Instruction Pointer)** — содержит адрес следующей инструкции, которую процессор будет исполнять. Нельзя изменить явно; обновляется инструкциями перехода (`jmp`, `call`, `ret`).

**RFLAGS** — регистр флагов. Каждый бит имеет смысл:
- **ZF** (Zero Flag) — результат последней операции равен нулю
- **CF** (Carry Flag) — произошёл перенос/заём из старшего бита
- **SF** (Sign Flag) — результат отрицательный (старший бит = 1)
- **OF** (Overflow Flag) — переполнение при знаковой арифметике
- **IF** (Interrupt Flag) — разрешены ли аппаратные прерывания

```c
// В C: локальная переменная может жить в регистре
int add(int a, int b) {
    int result = a + b;  // result — в регистре, не в памяти
    return result;
}
```

```asm
; Компилятор транслирует это в:
add:
    lea eax, [rdi + rsi]   ; EAX = RDI + RSI (сразу в регистр)
    ret
```

Переменная `result` нигде в памяти не появляется — она «живёт» только в регистре EAX.

### Ограниченность регистров и register spilling

Регистров всего 16 (общего назначения). Если компилятор работает с функцией, которая использует больше переменных, часть из них приходится «выгружать» (spill) в стек и снова загружать по мере необходимости. Это называется **register spilling** и является одной из причин, почему сложные функции с большим числом переменных работают медленнее — часть данных путешествует туда-обратно между регистрами и памятью.

## 2. Стек вызовов (Call Stack)

Стек — это область памяти, выделяемая для каждого потока исполнения. В типичном 64-битном Linux-приложении размер стека по умолчанию составляет 8 МБ (можно проверить командой `ulimit -s`).

### Принцип LIFO

Стек работает по принципу LIFO (Last In, First Out — последним пришёл, первым ушёл). Инструкции `PUSH` и `POP` работают с вершиной стека:

```asm
push rax    ; RSP -= 8; [RSP] = RAX
pop  rbx    ; RBX = [RSP]; RSP += 8
```

В x86-64 стек растёт от больших адресов к меньшим. Если стек начинается по адресу `0x7fff_ffff_f000`, то после `push rax` RSP станет `0x7fff_ffff_eff8`.

### Стековый фрейм (Stack Frame)

При вызове функции на стеке создаётся **стековый фрейм** — область памяти, содержащая:
1. Адрес возврата (return address) — адрес инструкции, следующей после `call`
2. Сохранённый RBP предыдущего фрейма
3. Локальные переменные функции
4. Сохранённые callee-saved регистры (RBX, R12-R15)

Визуализация стека при вложенных вызовах:

```
Высокие адреса
┌─────────────────────────────┐
│ Аргументы main (из ОС)      │
│ Аргументы командной строки  │
├─────────────────────────────┤  ← начальный RSP
│ Локальные переменные main() │
│ Сохранённый RBP             │
│ Адрес возврата из main()    │
├─────────────────────────────┤  ← RBP при вызове func_a
│ Локальные переменные func_a │
│ Сохранённый RBP main        │
│ Адрес возврата func_a       │
├─────────────────────────────┤  ← RBP при вызове func_b
│ Локальные переменные func_b │
│ Сохранённый RBP func_a      │
│ Адрес возврата func_b       │
├─────────────────────────────┤  ← текущий RSP
│   (свободная часть стека)   │
└─────────────────────────────┘
Низкие адреса
```

### Детальный разбор стекового фрейма

Рассмотрим функцию на C:

```c
long factorial(long n) {
    if (n <= 1) return 1;
    long prev = factorial(n - 1);
    return n * prev;
}
```

Разберём её ассемблерный код (GCC, -O1):

```asm
factorial:
    ; --- ПРОЛОГ ---
    push rbp            ; сохранить старый frame pointer
    mov  rbp, rsp       ; rbp = rsp (начало нашего фрейма)
    push rbx            ; сохранить rbx (callee-saved)
    sub  rsp, 8         ; выровнять стек до 16 байт

    ; --- ТЕЛО ---
    cmp  rdi, 1         ; if (n <= 1)
    jg   .recurse       ; если n > 1, идти к рекурсии
    mov  eax, 1         ; return 1
    jmp  .epilogue

.recurse:
    mov  rbx, rdi       ; rbx = n (сохраняем для умножения)
    lea  rdi, [rdi-1]   ; первый аргумент = n - 1
    call factorial       ; prev = factorial(n-1)
    imul rax, rbx       ; return n * prev

    ; --- ЭПИЛОГ ---
.epilogue:
    add  rsp, 8
    pop  rbx            ; восстановить rbx
    pop  rbp            ; восстановить старый frame pointer
    ret                 ; вернуться: RIP = [RSP]; RSP += 8
```

Обратите внимание на `sub rsp, 8` — это выравнивание. System V AMD64 ABI требует, чтобы RSP был выровнен по 16 байтам перед вызовом `call`. Поскольку `call` само кладёт на стек 8-байтовый адрес возврата, а `push rbp` добавляет ещё 8 байт, суммарно мы сдвинулись на 16 байт — выравнивание соблюдено. Но поскольку нам нужно сохранить rbx (ещё 8 байт), мы также добавляем `sub rsp, 8` для сохранения выравнивания перед вызовом `factorial`.

### Доступ к локальным переменным через RBP

При наличии frame pointer компилятор обращается к локальным переменным через RBP:

```c
void example(int a, int b) {
    int x = a + b;     // [rbp - 4]
    int y = a * b;     // [rbp - 8]
    int z = x + y;     // [rbp - 12]
}
```

```asm
example:
    push rbp
    mov  rbp, rsp
    sub  rsp, 16            ; место под x, y, z + выравнивание

    ; x = a + b
    mov  eax, edi           ; eax = a
    add  eax, esi           ; eax = a + b
    mov  DWORD PTR [rbp-4], eax   ; x = eax

    ; y = a * b
    mov  eax, edi
    imul eax, esi
    mov  DWORD PTR [rbp-8], eax   ; y = eax

    ; z = x + y
    mov  eax, DWORD PTR [rbp-4]   ; eax = x
    add  eax, DWORD PTR [rbp-8]   ; eax = x + y
    mov  DWORD PTR [rbp-12], eax  ; z = eax

    leave                   ; mov rsp, rbp; pop rbp
    ret
```

Смещения `[rbp-4]`, `[rbp-8]`, `[rbp-12]` — фиксированные адреса относительно frame pointer. Именно поэтому RBP называется «base pointer» — он является базой для доступа к локальным данным.

### Стек и Python

В Python каждый вызов функции создаёт **фрейм** (`frame object`) в куче виртуальной машины CPython — это аналог стекового фрейма, но управляемый интерпретатором:

```python
import sys

def inner():
    frame = sys._getframe()       # текущий фрейм
    print(f"Функция: {frame.f_code.co_name}")
    print(f"Файл: {frame.f_code.co_filename}")
    print(f"Строка: {frame.f_lineno}")
    print(f"Локальные: {frame.f_locals}")
    
    caller = frame.f_back         # фрейм вызывающей функции
    print(f"Вызвана из: {caller.f_code.co_name}")

def outer():
    x = 42
    inner()

outer()
# Вывод:
# Функция: inner
# Файл: example.py
# Строка: 4
# Локальные: {'frame': <frame object at 0x...>}
# Вызвана из: outer
```

В CPython стек интерпретатора реализован через связанный список объектов-фреймов в куче. Это медленнее, чем нативный стек C, но позволяет динамически анализировать и модифицировать стек во время работы программы.

## 3. Куча (Heap)

Куча — это область памяти для динамически выделяемых данных, жизненный цикл которых не привязан к вызову конкретной функции. В отличие от стека, куча управляется явно (malloc/free в C) или автоматически (GC в Python, Java; RAII в C++).

### Устройство кучи

Куча — это сплошная область памяти, которую менеджер кучи разбивает на блоки разного размера. Типичный менеджер кучи (например, ptmalloc2 в glibc) организует свободные блоки в связанные списки (bins) по размеру.

```
[Заголовок] [Данные пользователя] [Заголовок] [Данные] ...
```

Каждый блок содержит:
- Размер блока
- Флаги (занят/свободен, размер предыдущего блока)
- Указатели на соседние свободные блоки (если блок свободен)

```c
#include <stdlib.h>
#include <stdio.h>

int main() {
    // Выделить память в куче
    int *arr = malloc(100 * sizeof(int));
    if (arr == NULL) {
        perror("malloc failed");
        return 1;
    }
    
    // Использовать память
    for (int i = 0; i < 100; i++) {
        arr[i] = i * i;
    }
    
    printf("arr[50] = %d\n", arr[50]);  // 2500
    
    // Освободить память
    free(arr);
    // После free() указатель arr становится "висящим" (dangling pointer)
    // arr[0] = 1; // ОШИБКА! undefined behavior
    
    return 0;
}
```

### malloc и brk/mmap

Под капотом `malloc` использует системные вызовы Linux для получения памяти от ОС:

- **`brk()`** / **`sbrk()`** — расширяет сегмент данных процесса (для небольших выделений). Двигает «конец» кучи вверх.
- **`mmap()`** — создаёт новое отображение (для больших выделений, обычно > 128 КБ). Более гибко, но требует системного вызова.

```c
// Примитивный аллокатор (только для иллюстрации)
#include <unistd.h>

void *simple_malloc(size_t size) {
    void *ptr = sbrk(0);           // узнать текущий конец кучи
    if (sbrk(size) == (void*)-1) { // расширить кучу на size байт
        return NULL;               // системный вызов brk() не удался
    }
    return ptr;
}
// Этот аллокатор не поддерживает free() и фрагментацию — только для обучения!
```

### Динамическая память в Python

В Python каждый объект хранится в куче. Даже числа, строки и булевы значения — объекты в куче. Python использует собственный менеджер памяти поверх `malloc`, а также сборщик мусора (reference counting + cyclic garbage collector):

```python
import sys
import gc

# Показать размер объектов в куче
x = 42
print(sys.getsizeof(x))         # 28 байт (int в Python — объект!)

s = "hello"
print(sys.getsizeof(s))         # 54 байта

lst = [1, 2, 3]
print(sys.getsizeof(lst))       # 88 байт (список без учёта содержимого)

# Принудительная сборка мусора
gc.collect()

# Подсчёт ссылок
a = [1, 2, 3]
b = a                    # ещё одна ссылка на тот же список
print(sys.getrefcount(a))  # 3 (a, b, и аргумент getrefcount)

del a
print(sys.getrefcount(b))  # 2 (b и аргумент getrefcount)
del b
# После этого список освобождается (refcount = 0)
```

## 4. Стек против кучи: ключевые различия

### Скорость выделения памяти

**Стек**: выделение — это одна инструкция `sub rsp, N`. Освобождение — одна инструкция `add rsp, N` или `mov rsp, rbp`. Операция занимает 1 такт.

**Куча**: `malloc` требует поиска подходящего свободного блока (может быть O(1) при наличии кеша нужного размера, но иногда O(n)). При необходимости — системный вызов `brk`/`mmap`, что занимает тысячи тактов. `free` также требует слияния соседних блоков.

```c
#include <time.h>
#include <stdlib.h>
#include <stdio.h>

#define N 1000000

void bench_stack() {
    clock_t start = clock();
    for (int i = 0; i < N; i++) {
        int arr[100];  // выделение на стеке
        arr[0] = i;    // чтобы компилятор не оптимизировал
    }
    clock_t end = clock();
    printf("Stack: %.3f ms\n", 1000.0 * (end - start) / CLOCKS_PER_SEC);
}

void bench_heap() {
    clock_t start = clock();
    for (int i = 0; i < N; i++) {
        int *arr = malloc(100 * sizeof(int));  // выделение в куче
        arr[0] = i;
        free(arr);
    }
    clock_t end = clock();
    printf("Heap:  %.3f ms\n", 1000.0 * (end - start) / CLOCKS_PER_SEC);
}

int main() {
    bench_stack();
    bench_heap();
    return 0;
}
// Типичный вывод:
// Stack: 4.2 ms
// Heap:  187.6 ms  (в ~44 раза медленнее!)
```

### Фрагментация кучи

Многократное выделение и освобождение блоков разного размера приводит к **фрагментации**: куча содержит множество маленьких свободных блоков, но нет ни одного достаточно большого непрерывного блока для нового большого выделения.

```
До дефрагментации:
[ЗАНЯТ 8B][СВОБ 16B][ЗАНЯТ 32B][СВОБ 8B][ЗАНЯТ 64B][СВОБ 32B]
                                                    ↑
                    Нельзя выделить 40B, хотя суммарно 56B свободны!

После дефрагментации (если возможно):
[ЗАНЯТ 8B][ЗАНЯТ 32B][ЗАНЯТ 64B][СВОБ 56B]
                                          ↑
                    Теперь 40B можно выделить
```

В отличие от кучи, стек не страдает от фрагментации: все блоки освобождаются строго в обратном порядке (LIFO).

### Время жизни переменных

**Стек**: переменная существует только во время выполнения функции. Как только функция вернулась, её фрейм уничтожен.

```c
int* dangerous() {
    int local = 42;
    return &local;  // ОШИБКА! Возвращаем адрес локальной переменной
}                   // local уже не существует после возврата!

int main() {
    int *p = dangerous();
    printf("%d\n", *p);  // Undefined behavior! Данные уже перезаписаны
}
```

**Куча**: переменная существует до вызова `free` (C) или до сборки мусора (Python, Java). Это позволяет передавать данные между функциями через указатели/ссылки.

```c
int* safe() {
    int *heap_var = malloc(sizeof(int));
    *heap_var = 42;
    return heap_var;  // OK: данные в куче, живут после возврата
}

int main() {
    int *p = safe();
    printf("%d\n", *p);  // 42 — данные живы
    free(p);             // теперь освобождаем
}
```

### Размер

**Стек**: ограничен (обычно 1-8 МБ для потока). Попытка выделить больше приводит к **stack overflow**.

**Куча**: ограничена только доступной виртуальной и физической памятью. 64-битный процесс может иметь кучу размером в сотни гигабайт.

```c
// Stack overflow: рекурсия без базового случая
void infinite_recursion() {
    char big_array[1024];  // 1KB на каждый фрейм
    infinite_recursion();  // снова вызываем себя
}
// Через ~8000 вызовов: Segmentation fault (core dumped)
// Стек исчерпан!
```

## 5. Stack Overflow: причины и последствия

Stack overflow — это ошибка, возникающая при исчерпании стека. Наиболее частые причины:

### 1. Бесконечная рекурсия

```python
def factorial(n):
    return n * factorial(n - 1)  # Нет базового случая!

factorial(10000)
# RecursionError: maximum recursion depth exceeded
```

Python специально ограничивает глубину рекурсии (по умолчанию 1000 вызовов, можно изменить через `sys.setrecursionlimit`), чтобы избежать переполнения стека.

### 2. Слишком большие локальные массивы

```c
void process() {
    char buffer[8 * 1024 * 1024];  // 8 MB на стеке!
    // При обращении к buffer происходит Segmentation fault
    // (стек расширился за guard page)
}
```

### 3. Guard Page

ОС устанавливает специальную защитную страницу (guard page) в конце стека. При обращении к ней генерируется исключение (сегфолт в Linux), которое ОС перехватывает и заменяет сигналом SIGSEGV с сообщением «Stack overflow».

```bash
# Посмотреть размер стека и guard page:
cat /proc/self/maps | grep stack
# 7fffffff0000-7fffffffe000 rw-p [stack]  (8MB стек)

ulimit -s              # текущий лимит стека (в KB)
ulimit -s unlimited    # снять лимит (потенциально опасно)
```

## 6. Современные оптимизации: escape analysis

Современные компиляторы (Go, Java JIT, GCC с -O2) применяют **escape analysis** — анализ, который определяет, «вытекает» ли переменная за пределы функции. Если нет — переменная может быть размещена на стеке даже если синтаксически это выглядит как выделение в куче.

```go
// Go: escape analysis
func createPoint() *Point {
    p := &Point{X: 1, Y: 2}  // выглядит как куча
    return p                   // p "вытекает" → реально в куче
}

func noEscape() int {
    p := &Point{X: 1, Y: 2}   // выглядит как куча
    return p.X + p.Y           // p НЕ вытекает → оптимизируется в стек!
}
```

```bash
go build -gcflags='-m' main.go
# main.go:3:2: &Point literal escapes to heap
# main.go:8:2: &Point literal does not escape
```

В Java HotSpot JIT применяет аналогичный анализ — объекты с коротким временем жизни могут быть размещены прямо в стеке (stack allocation), избегая накладных расходов GC.

## 7. Thread Local Storage и несколько стеков

Каждый поток (thread) имеет свой собственный стек. При создании потока ОС выделяет для него новый стек:

```c
#include <pthread.h>
#include <stdio.h>

void* thread_func(void *arg) {
    int local_var = 42;  // локальная для этого потока
    printf("Thread stack var at: %p\n", &local_var);
    return NULL;
}

int main() {
    pthread_t t1, t2;
    int main_var = 0;
    printf("Main   stack var at: %p\n", &main_var);
    
    pthread_create(&t1, NULL, thread_func, NULL);
    pthread_create(&t2, NULL, thread_func, NULL);
    
    pthread_join(t1, NULL);
    pthread_join(t2, NULL);
}
// Вывод: три разных адреса — каждый поток в своей части адресного пространства
// Main   stack var at: 0x7ffd123a4bc0
// Thread stack var at: 0x7f8bc9e23b40
// Thread stack var at: 0x7f8bc961fb40
```

**Thread Local Storage (TLS)** — отдельный механизм для хранения переменных, которые уникальны для каждого потока, но должны быть доступны из разных функций (без явной передачи как параметр):

```c
// C11 TLS
_Thread_local int errno_value = 0;  // каждый поток имеет свою копию

// Python threading.local()
import threading
local_data = threading.local()
local_data.value = 42  // только для текущего потока
```

## 8. Адресное пространство процесса

Стек и куча занимают разные части виртуального адресного пространства процесса:

```
Виртуальное адресное пространство Linux x86-64 (64-битный процесс):
┌─────────────────────────────────┐ 0xFFFFFFFFFFFFFFFF
│       Ядро ОС (kernel space)    │
├─────────────────────────────────┤ 0xFFFF800000000000
│   (недоступная «дыра»)          │
│                                 │
├─────────────────────────────────┤ 0x00007FFFFFFFFFFF
│   Стек главного потока          │ ← RSP, растёт вниз ↓
│   (и стеки других потоков)      │
├─────────────────────────────────┤
│   mmap области (разд. библ.)    │
│   (общие библиотеки, анонимные) │
├─────────────────────────────────┤
│   Куча (heap)                   │ ← растёт вверх ↑
│   (malloc/free)                 │
├─────────────────────────────────┤
│   BSS  (uninit. globals)        │
│   Data (init. globals/statics)  │
│   Text (код программы)          │
└─────────────────────────────────┘ 0x0000000000400000
```

Стек и куча «растут навстречу» друг другу. В современных системах с ASLR (Address Space Layout Randomization) их расположение рандомизируется при каждом запуске для защиты от атак.

## Заключение

Регистры процессора — самый быстрый и самый ограниченный вид хранения: 16 регистров общего назначения, нет задержки доступа. Специальные регистры RSP, RBP и RIP управляют стеком и потоком исполнения.

Стек — линейная область памяти, работающая по принципу LIFO. Каждый вызов функции создаёт стековый фрейм с локальными переменными, сохранёнными регистрами и адресом возврата. Выделение на стеке — моментальное и бесплатное, но переменные живут только до завершения функции. Превышение размера стека приводит к stack overflow.

Куча — динамическая область для долгоживущих данных. Выделение требует работы менеджера кучи и иногда системного вызова. Куча страдает от фрагментации, но размер ограничен только доступной памятью, а время жизни объектов контролируется явно или сборщиком мусора.

Понимание разницы между тремя уровнями хранения — регистры, стек, куча — помогает писать более быстрый код, избегать типичных ошибок (dangling pointer, stack overflow, memory leak) и правильно интерпретировать сообщения профилировщика.
