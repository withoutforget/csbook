# Конвейеризация процессора (pipeline)

## Введение

Представьте автомобильный завод, где каждый рабочий выполняет только одну операцию: один устанавливает двигатель, другой крепит колёса, третий красит кузов. Пока первый рабочий устанавливает двигатель в машину №2, второй уже крепит колёса к машине №1. Именно этот принцип конвейерного производства лежит в основе одной из главных оптимизаций современных процессоров — конвейеризации (pipelining).

До появления конвейеров процессор полностью завершал выполнение одной инструкции, прежде чем приступить к следующей. При тактовой частоте 3 ГГц и 20-стадийном конвейере каждая стадия занимает около 0,3 наносекунды — именно дробление на стадии позволяет поднимать тактовую частоту. Без конвейера для выполнения одной инструкции за один такт потребовалась бы схема, успевающая за 0,3 нс пройти все этапы от выборки до записи результата — физически недостижимая задача при современных технологиях.

В этой статье мы разберём, как устроен процессорный конвейер, какие проблемы (hazards) возникают при его работе, как архитекторы процессоров решают эти проблемы с помощью forwarding, stall-ов и предсказания переходов, и как программист может писать код, дружественный к конвейеру.

## 1. Классический пятистадийный конвейер RISC

### 1.1 Стадии конвейера

Классический конвейер RISC-процессора (MIPS, ранний ARM) состоит из пяти стадий:

| Стадия | Английское название | Что происходит |
|--------|---------------------|----------------|
| IF | Instruction Fetch | Загрузка инструкции из памяти/кеша по PC |
| ID | Instruction Decode | Декодирование опкода, чтение регистров |
| EX | Execute | Выполнение арифметики в ALU, вычисление адреса |
| MEM | Memory Access | Чтение/запись данных из памяти/кеша |
| WB | Write Back | Запись результата в регистровый файл |

Без конвейера для выполнения N инструкций требуется 5N тактов. С конвейером (при отсутствии проблем) — N+4 такта. Для больших N ускорение стремится к 5×.

```
Такт:    1    2    3    4    5    6    7    8    9
Инстр1: IF   ID   EX  MEM   WB
Инстр2:      IF   ID   EX  MEM   WB
Инстр3:           IF   ID   EX  MEM   WB
Инстр4:                IF   ID   EX  MEM   WB
Инстр5:                     IF   ID   EX  MEM   WB
```

На такте 5 все пять стадий конвейера заняты одновременно — это и есть «конвейерный эффект».

### 1.2 Детальная работа каждой стадии

**Instruction Fetch (IF):** Программный счётчик (PC) указывает на адрес следующей инструкции. Схема загружает 32 или 64 бита из кеша инструкций (L1i). Затем PC инкрементируется (обычно на 4 байта для 32-битных инструкций). Результат — слово инструкции и значение PC+4 — передаётся в следующий регистр конвейера.

**Instruction Decode (ID):** Опкод декодируется, определяются номера регистров-источников и регистра-результата. Регистровый файл одновременно читается для получения операндов. Для немедленных значений (immediate) производится sign-extension.

**Execute (EX):** АЛУ (арифметико-логическое устройство) выполняет операцию: сложение, вычитание, AND, OR, сдвиг и т.д. Для инструкций обращения к памяти вычисляется эффективный адрес (base + offset). Для условных переходов вычисляется целевой адрес и проверяется условие.

**Memory Access (MEM):** Для инструкций LOAD — чтение из кеша данных (L1d). Для STORE — запись в кеш данных. Для всех остальных инструкций эта стадия проходит «вхолостую» (pass-through).

**Write Back (WB):** Результат из EX или MEM записывается обратно в регистровый файл. Это последняя стадия, после которой значение становится видимым для будущих инструкций.

## 2. Hazards — проблемы конвейера

Главная сложность конвейеризации — зависимости между инструкциями. Существуют три типа hazards:

### 2.1 Структурные опасности (Structural Hazards)

Возникают, когда два компонента схемы нужны одновременно разным стадиям. Классический пример: одна память и для инструкций, и для данных (архитектура Фон Неймана). Когда инструкция #1 обращается к памяти на стадии MEM, а инструкция #5 пытается загрузиться (IF) — оба обращаются к одной и той же памяти.

Решение: Гарвардская архитектура памяти внутри процессора — раздельные кеши L1i (инструкций) и L1d (данных). Именно поэтому все современные процессоры имеют раздельные кеши первого уровня, несмотря на общий L2/L3.

### 2.2 Опасности данных (Data Hazards)

Инструкция зависит от результата предыдущей инструкции, которая ещё не завершила запись.

```assembly
ADD R1, R2, R3    ; R1 = R2 + R3  (WB на такте 5)
SUB R4, R1, R5    ; R4 = R1 - R5  (ID на такте 3 — R1 ещё не готов!)
```

Выделяют три подтипа:

- **RAW (Read After Write)** — самый частый: инструкция читает регистр, который ещё не записан. «Истинная зависимость».
- **WAR (Write After Read)** — «антизависимость»: инструкция пишет в регистр, который более ранняя ещё не прочитала. В классическом конвейере не проблема (read всегда до write), но важно при out-of-order.
- **WAW (Write After Write)** — «выходная зависимость»: две инструкции пишут в один регистр. Важно при out-of-order и суперскалярности.

**Решение 1: Stall (пузырь конвейера)**

Вставка NOP-инструкций (или пузырей) для ожидания готовности результата:

```
Такт:     1    2    3    4    5    6    7    8
ADD:     IF   ID   EX  MEM   WB
STALL:        IF  ---  ---  ---
STALL:              ---  ---  ---
SUB:              IF   ID   EX  MEM   WB
```

За каждый пузырь теряется один такт. Для классического конвейера RAW-зависимость создаёт 2-3 пузыря.

**Решение 2: Forwarding (Bypassing)**

Вместо ожидания записи в WB, результат из EX-стадии или MEM-стадии «пробрасывается» напрямую на вход EX-стадии следующей инструкции:

```
ADD R1, R2, R3
         |
         | forwarding path: результат из EX → вход EX следующей инструкции
         ↓
SUB R4, R1, R5
```

```
Такт:     1    2    3    4    5    6    7
ADD:     IF   ID  [EX] MEM   WB
SUB:          IF   ID  [EX] MEM   WB
                    ↑    ↑
                    |    |
                    результат ADD пробрасывается из EX ADD → EX SUB
```

Forwarding добавляет мультиплексоры на входы АЛУ и логику определения зависимостей, но позволяет выполнять большинство зависимых инструкций без stall-ов.

**Когда forwarding не спасает — load-use hazard:**

```assembly
LW  R1, 0(R2)    ; загрузка из памяти, результат готов после MEM
ADD R3, R1, R4   ; нужен R1 уже в EX, но он ещё в MEM на такте LW
```

Даже с forwarding необходима вставка одного пузыря, так как данные из памяти приходят после MEM-стадии, а ADD нужны они в EX-стадии — разрыв в один такт неустраним.

### 2.3 Управляющие опасности (Control Hazards)

Возникают при инструкциях условного перехода. К моменту, когда условие вычислено (конец EX), конвейер уже загрузил несколько инструкций «по умолчанию». Если переход не взят — всё хорошо. Если взят — загруженные инструкции надо отменить (flush).

```assembly
BEQ R1, R2, label    ; условие вычисляется в EX (такт 3)
ADD R3, R4, R5        ; уже в ID (такт 3) — надо сбросить?
MUL R6, R7, R8        ; уже в IF (такт 3) — надо сбросить?
```

Цена неправильного предсказания — количество стадий конвейера после IF (обычно 15-20 тактов в современных процессорах).

**Решения:**
1. **Delayed branch slot** (MIPS): слот после инструкции перехода всегда выполняется. Компилятор заполняет его полезной инструкцией (или NOP).
2. **Branch prediction** (предсказание переходов) — тема следующей главы.
3. **Конвертация ветвей в предикатные инструкции** (ARM: MOVEQ, MOVNE и т.д.) — выполнять обе ветви, выбирать результат флагом.

## 3. Forwarding в деталях — реализация

Логика forwarding-блока: на каждом такте перед выполнением инструкции в EX проверяется, совпадают ли номера регистров-источников с номером результирующего регистра инструкции в MEM или WB.

```c
// Псевдокод логики forwarding (упрощённо)
if (EX_MEM.RegisterRd != 0 &&
    EX_MEM.RegisterRd == ID_EX.RegisterRs) {
    ForwardA = 10;  // использовать результат из EX/MEM
}
else if (MEM_WB.RegisterRd != 0 &&
         MEM_WB.RegisterRd == ID_EX.RegisterRs) {
    ForwardA = 01;  // использовать результат из MEM/WB
}
else {
    ForwardA = 00;  // использовать значение из регистрового файла
}
```

Аналогично для второго операнда (ForwardB). Мультиплексор на входе АЛУ выбирает источник в зависимости от ForwardA/ForwardB.

## 4. Суперскалярные процессоры

### 4.1 От скалярного к суперскалярному

Классический конвейер — «скалярный»: максимум одна инструкция на такт (IPC = 1). Суперскалярный процессор содержит несколько параллельных конвейеров и может выдавать (issue) несколько инструкций за такт.

Intel Pentium (1993) — первый массовый суперскалярный x86: 2 параллельных конвейера (U-pipe и V-pipe). Современные Intel/AMD — 4-6 инструкций за такт.

| Процессор | Год | Ширина выдачи | Длина конвейера |
|-----------|-----|---------------|-----------------|
| MIPS R2000 | 1985 | 1 | 5 |
| Intel Pentium | 1993 | 2 | 5 |
| Intel Pentium Pro | 1995 | 3 | 14 |
| Intel Core 2 | 2006 | 4 | 14 |
| Intel Skylake | 2015 | 4 (6 µops) | 14-19 |
| AMD Zen 4 | 2022 | 4 | 19 |
| Apple M2 | 2022 | 8 | ~16 |

### 4.2 Out-of-Order Execution (OOO)

In-order суперскалярный процессор (простой, но ограниченный): инструкции выдаются и завершаются строго по порядку программы. Если инструкция #3 ждёт данных от инструкции #2 (stall), то инструкция #4 тоже вынуждена ждать, даже если у неё нет зависимостей от #2 или #3.

Out-of-order (OOO) процессор решает эту проблему: инструкции могут выполняться в другом порядке, если между ними нет зависимостей, но результаты фиксируются в порядке программы (commit in-order).

Ключевые компоненты OOO:

1. **Instruction Window / Reservation Stations:** буфер для хранения инструкций, ожидающих операндов. Инструкция выходит в выполнение, как только все её операнды готовы.

2. **Register Renaming:** устраняет ложные WAR и WAW зависимости. Каждое «программное» имя регистра (архитектурный регистр) маппируется на один из большого банка физических регистров. Intel Skylake: 168 физических регистров против 16 архитектурных.

3. **Reorder Buffer (ROB):** хранит инструкции в программном порядке до момента commit. Это обеспечивает «видимость» правильного порядка выполнения для внешнего мира и позволяет отменять инструкции при неверном предсказании перехода.

```
Pipeline современного OOO процессора (Intel):

Fetch → Predecoder → Instruction Cache → Decode → Allocator/Renamer → 
Dispatch → [Reservation Stations] → Execution Units → ROB → Retire
```

### 4.3 Влияние на программиста

Пример: два независимых вычисления в одном цикле.

```c
// Плохо — зависимость через sum создаёт цепочку зависимостей:
double sum = 0.0;
for (int i = 0; i < N; i++) {
    sum += a[i];  // каждая итерация зависит от предыдущей
}

// Лучше — развёртка цикла позволяет OOO скрыть задержку FP-сложения:
double sum0 = 0.0, sum1 = 0.0, sum2 = 0.0, sum3 = 0.0;
for (int i = 0; i < N; i += 4) {
    sum0 += a[i];
    sum1 += a[i+1];
    sum2 += a[i+2];
    sum3 += a[i+3];
}
double sum = sum0 + sum1 + sum2 + sum3;
```

Задержка FP-сложения на современных CPU — 4 такта. Четыре независимые суммы позволяют скрыть эту задержку при throughput FP-сложения 0.5 такта (2 сложения за такт).

## 5. Влияние компилятора

### 5.1 Instruction Scheduling

Компилятор знает задержки инструкций и может переставить их так, чтобы зависимые инструкции не шли подряд:

```c
// Исходный C код:
a = b + c;
d = a * 2;
e = f + g;

// Наивная генерация кода:
ADD R1, R2, R3     ; a = b + c
MUL R4, R1, #2    ; d = a * 2  ← RAW hazard на R1 (2-3 stall'а)
ADD R5, R6, R7    ; e = f + g

// После scheduling компилятора:
ADD R1, R2, R3     ; a = b + c
ADD R5, R6, R7    ; e = f + g  ← независимо, заполняет стоп
MUL R4, R1, #2    ; d = a * 2  ← R1 уже готов (1-2 такта прошло)
```

GCC и Clang выполняют instruction scheduling как одну из стандартных оптимизаций. Флаг `-O2` включает его.

### 5.2 Loop Unrolling

Развёртка цикла уменьшает overhead на проверку условия и увеличивает число независимых операций:

```c
// Компилятор может превратить:
for (int i = 0; i < n; i++) {
    c[i] = a[i] + b[i];
}

// В (при -O3):
for (int i = 0; i < n - 3; i += 4) {
    c[i]   = a[i]   + b[i];
    c[i+1] = a[i+1] + b[i+1];  // независимо от предыдущего
    c[i+2] = a[i+2] + b[i+2];  // независимо
    c[i+3] = a[i+3] + b[i+3];  // независимо
}
// + остаток
```

Четыре сложения независимы — OOO процессор может выполнять их параллельно. Clang делает это автоматически с `-O3`.

### 5.3 Software Pipelining

Более агрессивная техника: итерации цикла «перемежаются» так, чтобы нагрузка между разными итерациями была независима:

```assembly
; Обычный цикл для a[i] = b[i] + c[i]:
loop:
    LD    R1, [b+i]        ; load b[i]
    LD    R2, [c+i]        ; load c[i]  
    ADD   R3, R1, R2       ; add (ждёт load)
    ST    R3, [a+i]        ; store

; Software pipelined (итерация i загружает, итерация i-1 суммирует):
    LD    R1, [b+0]
    LD    R2, [c+0]
loop:
    ADD   R3, R1, R2       ; add данных из предыдущей итерации
    LD    R1, [b+i+1]      ; загрузка для следующей итерации
    LD    R2, [c+i+1]      ; (пока ADD выполняется)
    ST    R3, [a+i]
```

## 6. Примеры работы конвейера на реальном коде

### 6.1 Почему цикл без зависимостей быстрее

```c
// Вариант 1: зависимость через acc (цепочка RAW)
long dependent_sum(long *a, int n) {
    long acc = 0;
    for (int i = 0; i < n; i++) {
        acc += a[i];  // acc[i] зависит от acc[i-1]
    }
    return acc;
}

// Вариант 2: независимые суммы
long independent_sum(long *a, int n) {
    long acc0 = 0, acc1 = 0, acc2 = 0, acc3 = 0;
    for (int i = 0; i < n - 3; i += 4) {
        acc0 += a[i];
        acc1 += a[i+1];
        acc2 += a[i+2];
        acc3 += a[i+3];
    }
    return acc0 + acc1 + acc2 + acc3;
}
```

Практический результат на Skylake (задержка ADD = 1 такт, но throughput = 4/такт):
- Вариант 1: ~1 такт/элемент (bottleneck — цепочка зависимостей)
- Вариант 2: ~0.25 такта/элемент (4 независимых сложения параллельно)

Ускорение 4× просто от перестановки вычислений!

### 6.2 Измерение IPC

```bash
# Подсчёт IPC с помощью perf (Linux):
perf stat -e instructions,cycles ./program

# Вывод:
# instructions: 1,234,567,890
# cycles:         987,654,321
# IPC = 1,234,567,890 / 987,654,321 = 1.25

# Высокий IPC (> 3) — хорошо используется суперскалярность
# Низкий IPC (< 1) — много stall'ов (память, зависимости, ошибочные предсказания)
```

### 6.3 Анализ с помощью LLVM-MCA

LLVM Machine Code Analyzer анализирует статически, как код выполняется на конвейере:

```bash
# Компилируем с флагами для получения asm:
clang -O2 -S -masm=intel -o output.s input.c

# Анализируем:
llvm-mca -mcpu=skylake output.s

# Вывод показывает:
# - Throughput (инструкции/такт)
# - Bottleneck (какой порт перегружен)
# - Цепочки зависимостей
```

## 7. Длина конвейера и её компромиссы

### 7.1 Почему Intel увеличивал конвейер

Intel Pentium 4 (Prescott) — печально известный 31-стадийный конвейер. Цель: достичь 4+ ГГц. Каждая стадия укорачивается (меньше логики → быстрее), позволяя повысить тактовую частоту.

Проблемы:
- Цена misprediction возросла до 20-31 такта
- Потребление и тепловыделение росли непропорционально
- IPC упал из-за большего числа пузырей

Intel Core (2006) вернулся к 14-стадийному конвейеру с более умным предсказателем — и оказался быстрее Pentium 4 при меньшей частоте.

### 7.2 Оптимальная длина

Компромисс: короткий конвейер → меньше частота, но меньше цена misprediction. Длинный конвейер → выше частота, но дороже ошибки.

Современная тенденция (ARM, Apple): конвейеры умеренной длины (15-20 стадий) с очень умными предсказателями переходов (точность 98%+).

## 8. Суперскалярность vs VLIW

### 8.1 VLIW (Very Long Instruction Word)

Альтернативный подход: вместо того чтобы CPU динамически обнаруживал параллелизм (OOO), компилятор явно упаковывает параллельные операции в «очень длинное слово инструкции».

```
VLIW-слово (Itanium IA-64 bundle, 128 бит):
[ инструкция 1: ALU  | инструкция 2: FPU | инструкция 3: MEM ]
```

Плюсы: простая аппаратура (нет ROB, нет reservation stations), предсказуемая производительность.  
Минусы: компилятор должен знать задержки каждой инструкции; бинарная несовместимость при изменении микроархитектуры; разреженные VLIW-слова при недостатке параллелизма.

Intel Itanium (1999-2017) — главная реализация. Несмотря на теоретические преимущества, проиграл x86-64 из-за сложности компилятора и плохого ILP в реальных программах.

### 8.2 Сравнение подходов

| Характеристика | Суперскалярный OOO | VLIW |
|---------------|-------------------|------|
| Обнаружение параллелизма | Аппаратно (runtime) | Компилятор (compile-time) |
| Сложность | CPU очень сложный | Компилятор очень сложный |
| Совместимость | Бинарная совместимость | Нет без перекомпиляции |
| Предсказуемость | Нет | Да |
| Применение | Intel/AMD/ARM | DSP, GPU shader units |

## 9. Практические выводы для программиста

### 9.1 Что замедляет конвейер

1. **Цепочки зависимостей** — избегайте длинных цепочек RAW. Развёртывайте циклы, используйте несколько аккумуляторов.

2. **Branch misprediction** — ветвление в горячих путях кода. Рассмотрите branchless-варианты (cmov, предикатные инструкции).

3. **Cachemiss** — самая дорогая остановка (100-300 тактов для RAM). Cache-friendly паттерны доступа — важнее всего.

4. **Long-latency инструкции** — целочисленное деление (20-90 тактов!), трансцендентные функции.

### 9.2 Branchless код

```c
// Версия с ветвью:
int max_branch(int a, int b) {
    if (a > b) return a;
    else return b;
}

// Версия без ветви (cmov):
int max_branchless(int a, int b) {
    return a > b ? a : b;  // Компилятор генерирует CMOV на -O2
}
```

```assembly
; gcc -O2 генерирует для max_branchless:
cmp     edi, esi
mov     eax, esi
cmovge  eax, edi    ; conditional move — не прерывает конвейер
ret
```

### 9.3 Измерение производительности конвейера

```python
# Профилирование горячих функций на Python (cProfile + line_profiler)
import cProfile
cProfile.run('your_function()')

# Но для измерения pipeline-эффектов нужны hardware counters:
# - Linux perf
# - Intel VTune
# - AMD uProf
```

```bash
# Подсчёт pipeline stalls с perf:
perf stat -e \
  cpu/event=0x0E,umask=0x01,name=uops_issued_stall_cycles/ \
  -e cache-misses \
  -e branch-misses \
  ./your_program
```

## Заключение

Конвейеризация — фундаментальная техника, позволившая процессорам достичь GHz-частот при разумной сложности схем. Понимание её работы объясняет многие «магические» явления производительности:

- Почему суммирование элементов массива с несколькими аккумуляторами быстрее (параллелизм на уровне инструкций, скрытие задержек)
- Почему деление медленнее умножения (нет эффективного конвейерного деления)
- Почему if-else в горячем цикле дороже, чем кажется (misprediction penalty)
- Почему компилятор переставляет инструкции (instruction scheduling)

Современные OOO-процессоры с суперскалярной выдачей, переименованием регистров и спекулятивным выполнением — это «промышленный конвейер», работающий на грани своих возможностей. Понимание этих механизмов позволяет писать код, который использует эти возможности максимально.

Следующая тема — предсказатель переходов (branch prediction) — напрямую связана с управляющими опасностями конвейера. Именно качество предсказания определяет, насколько редко конвейер сбрасывается при условных переходах.
